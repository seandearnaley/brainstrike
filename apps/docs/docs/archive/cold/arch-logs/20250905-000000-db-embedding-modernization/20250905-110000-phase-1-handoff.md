## 🔧 Root Cause & Fix

### Root Cause
- In Node tests we passed `:memory:` to PGlite, which created a real folder named `:memory:` at the repo root, persisting the cluster across tests. This caused migrations/state reuse and triggered a PGlite MultiXact wraparound error intermittently.

### Fix (2025 best-practice)
- Use true in-memory data dirs: `memory://` for ephemeral DBs in both Node and browser.
- Normalize legacy usages so tests are hermetic:
  - Mapped `':memory:' -> 'memory://'` inside `wasm-loader` for all callers.
  - Updated test suites and helpers to use `memory://` explicitly.
- Result: fresh cluster per test, no persistent MultiXact state, no flake.

### Validation
- Re-ran `packages/db/__tests__/file-record-repository.test.ts` 6x in isolation: 0/6 failures.
- Broader package tests run clean in this environment; any EPERM signals seen were sandbox-related process-kill noise, not test failures.

## 🕵️ Investigation Outcome

### Answers
1. Pre-existing vs Phase 1: confirmed unrelated to Phase 1 logic; it was a test DB lifecycle issue.
2. PGlite version: not version-specific; misuse of `:memory:` on Node caused persistence.
3. Test ordering: issue stemmed from reusing the same on-disk cluster, not order per se.
4. Reproduction: reproduced intermittently; fully eliminated after switching to `memory://`.

### Implemented Changes
- Code
  - `packages/db/src/wasm-loader.ts`: always uses `memory://` for temporary WASM load; maps `:memory:` -> `memory://` for callers; avoids passing undefined to the constructor.
- Tests
  - `packages/db/__tests__/file-record-repository.test.ts`: switched to `memory://`.
  - `packages/db/__tests__/clear-data.test.tsx`: wrappers and mocks now use `memory://`.
  - `packages/db/__tests__/db-provider*.test.tsx`: wrappers/mocks use `memory://`.
  - `packages/db/__tests__/wasm-loader-coverage.test.ts`: coverage paths updated to `memory://`.
- Docs
  - `packages/db/README.md`: examples updated to recommend `memory://` over `:memory:`.
