# Foreground latency under a full index build

## BST-1925 instrument and BEFORE numbers — 2026-10-02

Working rule 4 reads: no new scheduler, budget, throttle, retry or timeout
without before/after foreground p95 from the loaded benchmark. This is that
benchmark. It runs a full Workspace Index build of a seeded corpus in the real
desktop app and measures what a user doing foreground work feels while the
build runs. It reports and does not gate: the spec fails only when a run cannot
produce valid numbers (precedent: `embedding-queue-load.integration.test.ts`).

- Spec: `apps/desktop/e2e/foreground-latency-under-index-build.desktop.test.ts`
  (Playwright project `perf`, never in `regression`; the project exists only
  with `BRAINSTRIKE_E2E_PERF=1`, so a plain `playwright test` never runs it).
- Probes: `apps/desktop/e2e/utils/foreground-latency-probes.ts`.
- Corpus: `apps/desktop/e2e/utils/index-build-corpus.ts`.
- E2E-only main-process seam: `apps/desktop/src/e2e-foreground-latency-probes.ts`.
- Shared setup and reporting: `apps/desktop/e2e/utils/foreground-latency-bench.ts`.

Since 2026-10-15 (BST-2012, evidence schema v3) both foreground probes run
through their current owners: the chat-path op is one committed agent-host
command and the tool read's index half is the grep tool's native index query.
Desktop PGlite is gone (#3595), so v2 and earlier chat-path and index-query
numbers measure retired paths and do not compare with v3. The evidence also
records when each stage's receipts completed and the hidden embedding host's
isolation, CPU and memory. This benchmark replaces the retired desktop stage
benchmark (`workspace-index-stage-benchmark`), whose PGlite stages the native
index no longer runs.

Since 2026-10-09 the spec builds the **native** Workspace Index (M3:
`NativeWorkspaceIndexProvider` and the native indexer process). The legacy
pipeline it was written against (the renderer's sync orchestration, the
`__BRAINSTRIKE_WORKSPACE_INDEX_DEBUG__` summary and the backfill `complete`
event) no longer runs in the desktop, so the BEFORE numbers below describe a
pipeline that no longer exists; compare native runs with native runs (see
"Native index runs").

### How a run works

1. Write the corpus: seed 1925, `N` TypeScript files generated by a fixed PRNG.
   The evidence records the corpus SHA-256; runs compare only when it matches.
2. Show the app window (inactive, so it takes no focus). Desktop E2E otherwise
   never shows it, and a never-shown window on Linux runs rAF at about 1 Hz.
3. Open it as the workspace root with the Workspace Index **paused**. In
   Settings → Search & Indexing, choose BGE Small, "Text and semantic search"
   and the device's execution plan (`WebGPU · FP16`, or `WASM · Q8`); the
   index stays paused. Start one agent-host thread through main's host client
   for the chat-path probe, and wait until the paused index has activated
   (its reads refuse while it transitions; activation embeds on the configured
   device, so a device too slow for its request deadline fails here).
4. Calibrate the renderer probe: block the renderer's main thread for 120 ms and
   require the long-task observer to record it and the frame gap to show it.
   A dead observer would otherwise report "zero long tasks".
5. **Idle:** 10 warm-up operations per probe, outside every window. Then the
   renderer window opens, main runs exactly 150 samples per foreground probe
   at one every 200 ms (about 30 s) with its event-loop histogram on, and the
   renderer window closes.
6. **Loaded:** open the indexing status popover, then start the main probes
   and open the renderer window just before clicking Resume (the two start
   within one CDP round trip). The window includes the click and closing the
   popover. Every 2 s (`CHECK_EVERY_MS`) the test pauses both windows, reads
   the native index through the renderer's `indexSearch` capability
   (`status()` and `coverageBatch()` over the authorized roots), and resumes,
   so the checks are never measured. The loaded window closes at the first
   check that finds every root's scan complete, every corpus file indexed,
   every chunk embedded and no vector missing, so it can run up to one check
   interval past the build's real end. Probes keep their 200 ms pace
   throughout. A loaded window has many segments; the evidence records how
   many (`loadedWindowSegments`).
7. Write the evidence JSON, print a summary, and fail if the run is invalid.

A run is **invalid**, never reported, when: the build took under 60 s; any
probe has fewer than 100 loaded samples; any probe operation threw; the idle
rAF frame gap p50 is above 20 ms (the window is not producing frames); the
calibration block was not seen; the native query plan
(`queryPlan.inferencePlan.device`) runs on another device than configured; or
the index stopped making progress (the stall rule below). An invalid run still writes its
evidence, with `status: "invalid"` and the reasons.

#### Stall rule

If no index count (indexed files, chunks, embedded chunks) changes for 200 s,
the run stops, records the last index summary as an invalid reason and writes
its evidence, instead of hanging until the 55-minute test timeout. The loop
checks every 2 s, so it stops within 2 s of that window.

The window is sized from observed progress. In traces read every ~1.2 s, the
slowest gap between count changes was 6.1 s: the WASM model loading before the
first embedding (60 files); at most 7.3 s given the read interval. The WebGPU
path (1,000 files) never went longer than 1.3 s without a change. CI's WASM
path is up to 2.7× slower (1.68 against 4.49 chunks/s), so its slowest gap
should be about 20 s. 200 s is a 10× margin on that.
`index-progress-watch.ts` holds the decision; `pnpm test:scripts` tests it
(`scripts/__tests__/index-progress-watch.test.mjs`), because a build that never
finishes cannot be produced on demand in the real app.

### The metric set

| Metric | Definition | Why it is in the set |
| --- | --- | --- |
| Renderer frame gap p50, p95, max | Time between consecutive `requestAnimationFrame` callbacks in the visible window. 16.7 ms at 60 Hz. | Jank is felt in the visible renderer, which runs today's sync orchestration. A gap over 50 ms is a visible stall. |
| Renderer long tasks: count, total ms | `PerformanceObserver` `longtask` entries (main-thread tasks over 50 ms) in the visible window. | Names the cause of a frame gap. The M2 exit criterion requires zero. |
| Main event-loop lag p95, max | `perf_hooks.monitorEventLoopDelay` at 10 ms resolution, minus the resolution, so 0 means on time. | Main brokers every IPC call, every chat-path write and every tool call. Its lag adds to all of them. |
| Chat-path op p95, max | One agent-host `thread/update` command (a probe thread's title) through main's host client, timed in main until the host answers. | See below. |
| Tool read p95, loaded ÷ idle | The shared tool file reader (`readWorkspaceTextFile`) on a fixed corpus file, then the grep tool's index half (`nativeGrepIndex` over the native index's query host), scoped to one never-indexed path. Timed in main. | An agent's tools read while a build runs. The loaded÷idle ratio is the contention signal. |
| Build throughput | Embedded chunks ÷ build wall time (Resume to the first check that finds the index terminal). The fields keep the retired stage benchmark's names: `chunkCount`, `completedChunkCount`, `elapsedMs`, `chunksPerSecond`. | M2's second exit criterion, and the context for every other number: a faster build is a heavier load. |

The evidence also keeps the tool read's two components (file read, index
query), p50s, `n` everywhere, and the raw chat-path and tool-read samples, for
diagnosis. They are not part of the metric set. Two further records give the
build's context, read at each unmeasured check:

- `build.stageMilestonesMs`: when the first chunk, every file's chunks, the
  first vector and every vector were committed, in ms after Resume, at the
  check resolution. Chunking and embedding complete separately, so a change
  can say which stage it moved.
- `embeddingHost`: the hidden embedding host's `crossOriginIsolated` and
  `navigator.hardwareConcurrency`, its process CPU and its peak working set,
  from `app.getAppMetrics()`. Electron reports CPU as a percent of all cores
  since the previous check, so on 16 cores one busy thread reads about 6% and
  ONNX Runtime's four WASM threads about 25%.

#### Chat-path op: why one host command

A streamed run's events, a thread's title and every other conversation fact are
appended by the agent host through its single StateStore writer, and the
visible window reaches the host over its client protocol. One `thread/update`
command is the smallest request that takes that whole path: the client
protocol, the host's command admission, one committed append and the answer.

- It waits on whatever the host's writer is doing, as each run event does.
- It is short and does not grow with the conversation, so idle and loaded
  samples do the same work; a full run would add provider and message-size
  variance unrelated to contention.
- It is timed in main through main's own host client, the same process that
  times the tool read, so both probes share one clock and one event loop.

The probe commits a new title to one probe thread every 200 ms.

#### Tool read: why the index query targets a path that is never indexed

The ratio only means contention if the work is identical idle and loaded. The
file read reads the same corpus file every time. The index query is the grep
tool's native query scoped to `packages/foreground-latency-probe/never-indexed.ts`,
which no build ever writes: it returns nothing, in both phases. Pointing it at a
corpus file would return zero rows idle and real rows once that file is indexed,
so the ratio would mix data growth into contention.

### Running it

Locally, from the repository root (it builds the desktop app first, as every
local desktop E2E run does):

```bash
node apps/desktop/scripts/benchmark-workspace-index-pipeline.mjs \
  --mode integrated --require-device webgpu --files 1000
```

This runs the `test:e2e:lane:foreground-latency` lane (which sets
`BRAINSTRIKE_E2E_PERF=1`) and prints the validated evidence (raw samples
omitted) as JSON. The lane can also be run directly from `apps/desktop`. The
spec reads:

| Variable | Default | Meaning |
| --- | --- | --- |
| `BRAINSTRIKE_WORKSPACE_INDEX_INTEGRATED_BENCHMARK_DEVICE` | `webgpu` | Embedding device (`webgpu` or `wasm`); the product default is `webgpu`. |
| `BRAINSTRIKE_WORKSPACE_INDEX_INTEGRATED_BENCHMARK_FILES` | `1000` | Corpus size. Raise it when a faster build drops under the 60 s floor. |
| `BRAINSTRIKE_WORKSPACE_INDEX_INTEGRATED_BENCHMARK_EVIDENCE_PATH` | Playwright output dir | Where the evidence JSON goes. |

`--evidence <path>` re-validates and prints a recorded evidence file without
running anything. With `--require-device`, both the configured and the actual
embedding device must match, or the command fails.

In CI, the `Desktop Foreground Latency Benchmark` job in
`.github/workflows/desktop-e2e.yml` runs nightly and on dispatch, never on pull
requests:

```bash
gh workflow run desktop-e2e.yml --ref <branch> -f suite=foreground-latency
```

Runners have no GPU, so CI embeds on `wasm` with 60 files. The evidence is the
`desktop-foreground-latency-evidence` artifact.

Compare a change only against BEFORE numbers from the same environment, device
and corpus. Local and CI numbers measure different load: WebGPU on an M4 Max
completes about 42 chunks/s and keeps the DB host busy; WASM on a 2-vCPU runner
completes under 2 chunks/s, so its load is mostly CPU.

Where the spread exceeds ±20%, and why:

- **Loaded p95s are stable.** Locally every loaded p95 is within ±1–6%. On CI
  they are within ±14–17% across CPU models and ±5–7% on one model. Those are
  the numbers rule 4 compares.
- **Tool-read idle p95 and the loaded÷idle ratio (±60%, ±51%).** The cause is
  the file-read component. `readWorkspaceTextFile` makes dozens of small
  file-system calls through libuv's thread pool (path resolution, a `.git`
  search up to the filesystem root, a `.llmignore` and `.brainstrikeignore`
  lookup in every directory down to the file, stat, read), so it is at the
  mercy of other processes' disk and CPU activity. This machine was shared with other
  agents' builds and test runs throughout; in run 2 the file read's idle p95 was
  23.1 ms against 5.0 and 7.4 ms in the others, and its loaded p95 jumped too.
  The index-query component, the part the build actually contends for, stayed
  within ±13% idle and ±1% loaded. A shake-down run at load average 15 gave a
  ratio of 2.67 for the same reason.
- **Main lag idle p95 (±22% local, ±38% CI).** Small absolute values (0.5–4.6
  ms) on an idle app; loaded p95 is ±6% local and ±15% CI.
- **Maxima (±15–45%)** are single samples and move with any one stall; they
  are reported, not compared.

So for rule 4: compare loaded p95s against the same environment's BEFORE.
Read the tool-read ratio as the median of three runs on a quiet machine (the
evidence records the load average), and check the index-query component beside
it.

### M2 exit thresholds

Read an AFTER run against the BEFORE run from the same environment:

| Criterion | Threshold |
| --- | --- |
| Renderer during the build | max frame gap < 50 ms and zero long tasks |
| Chat-path op | loaded p95 ≤ BEFORE loaded p95 + 5 ms |
| Tool read | loaded p95 ≤ 2 × idle p95 of the same run |

### Known limits

- The benchmark shows the app window, which desktop E2E otherwise never does;
  local runs put a window on screen for a few minutes. The idle frame-gap check
  and the calibration block prove that rAF and the long-task observer work.
- Probes are paced, not open-loop: an operation that overruns its 200 ms slot
  delays the next one. A long stall therefore yields one slow sample rather
  than several queued ones, so p95 understates queueing during stalls; max
  still shows the stall.
- The embedding host is stopped while indexing is paused, so the loaded window
  includes its start and model load. That is what Resume does in the app.
- On macOS the tool read's file component was slower idle than loaded in every
  quiet run (idle p95 4.9–7.4 ms, loaded p95 1.2 ms). That inflates the
  tool-read idle denominator, so the ratio understates contention; the
  index-query component shows the contention directly. The cause is not
  isolated: an A/B check with Electron's `prevent-app-suspension` power blocker
  changed nothing.
