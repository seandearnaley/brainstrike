Brainstrike now treats a PR as two linked claims: the code changed, and the right local proof was run for that exact code. The `.ci/proof/latest.json` file is the machine-readable receipt that makes that claim checkable by GitHub.

01 / Summary

What Is The .ci Proof System?

It is a local-first PR gate. Before a branch goes to GitHub, the repo decides what risk the diff introduced, runs the matching local proof commands, writes a JSON receipt, and then GitHub verifies that receipt against the live PR.

It is not a cache

The proof file does not make tests pass. It records that specific commands already passed for a specific commit.

It is not optional decoration

PR Sentinel recomputes the risk selection and fails when proof is missing, stale, structurally invalid, or missing labels.

It is not a replacement for CI

CI still runs cloud lanes. Proof makes cloud CI a verification loop instead of the first time the branch is tested honestly.

The core invariant

Source/config/test/doc changes must be committed first. Then proof is generated. Then .ci/proof/latest.json is committed by itself as the final proof-only commit. Any later source change invalidates the proof.

02 / Model

The Mental Model

Think of a PR like a science experiment. The code commit is the sample. The proof file is the lab report. If you change the sample after writing the report, the report is no longer valid.

Old habit
change code -> maybe run tests -> push -> wait for CI to explain risk
New habit
change code -> select risk -> prove locally -> commit proof -> CI verifies
Question Answer
Why have a proof file at all? Because chat, PR descriptions, and memory are not reliable evidence. A JSON file tied to a git SHA is checkable.
Why commit proof separately? So the repo can detect whether any real code changed after the tested commit. Only the proof file is allowed to change after testedHeadSha.
Why labels? GitHub workflow jobs are label-routed. The selector says which labels are required; PR Sentinel verifies they are present.
Why still run CI? Local proof catches errors early and records intent. CI proves the same branch in the cloud environment and gates merge.
03 / Workflow

The Required PR Workflow

This is the operating procedure for every PR targeting main. For another target branch, replace origin/main with that target ref.

  1. 1
    Commit all real changes except proof.

    Source, config, workflow, tests, and docs go into normal commits. Do not include .ci/proof/latest.json yet.

  2. 2
    Select the risk lanes.

    Run pnpm ci:select --base origin/main --head HEAD. Read the selected labels and commands before doing anything expensive.

  3. 3
    Create or update the PR with the selected labels.

    When creating a PR, prefer passing labels at creation time if possible. If labels are added after the PR opens, the first workflow run may not see them.

  4. 4
    Run local proof on a clean worktree.

    pnpm ci:prove --base origin/main --head HEAD refuses to run with dirty files. That is intentional: proof must correspond to committed code.

  5. 5
    Commit proof by itself.

    Add and commit only .ci/proof/latest.json. The commit message should make clear this is proof-only.

  6. 6
    Verify before push.

    Run pnpm ci:verify-proof --base origin/main --head HEAD --labels "ci:...". This catches stale proof locally before GitHub does.

  7. 7
    Push and monitor the latest-head run.

    If you push another source change, repeat selection, proof, proof-only commit, and verification. Cancel superseded cloud runs when appropriate.

# Typical PR path targeting main
git status --short
pnpm ci:select --base origin/main --head HEAD

# Add selected ci:* labels to the PR.
# Then run local proof:
pnpm ci:prove --base origin/main --head HEAD

git add .ci/proof/latest.json
git commit -m "Record local proof for <change>"

pnpm ci:verify-proof --base origin/main --head HEAD --labels "ci:full"
git push
04 / Manifest

What Is In .ci/proof/latest.json?

The manifest is deliberately boring. It records environment, selected risk, selected commands, command results, timings, budgets, and the git SHA that was tested.

Field Meaning Why PRs Care
testedHeadSha The exact 40-character commit SHA that was tested. Verification ensures this SHA is an ancestor of the PR head and that only the proof file changed after it.
selection.files The changed files used for risk selection. Explains why a PR selected cheap, desktop, web, DB, embedding, or full lanes.
selection.riskProfile The named risk category, owning domains, E2E lanes, proof commands, and cloud labels. Prevents "why did this run?" confusion during review.
selection.labels The exact ci:* labels required on the PR. PR Sentinel fails if any required label is missing. Extra labels are allowed.
selection.commands The local commands that were supposed to run for the selected risk. Verification recomputes this selection and fails if the manifest no longer matches.
commandResults Each command's exit code, duration, budget, owner, and budget status. Shows both correctness and cost. A command result with nonzero exit code invalidates proof.
packageManager / pnpmVersion The package manager version used for proof. Prevents proof produced with the wrong toolchain from passing as official evidence.
05 / Labels

Labels And Risk Lanes

The selector maps changed files to risk lanes. Labels are the bridge between local selection and cloud jobs.

ci:browser ci:web-smoke ci:web-file-explorer-persistence ci:web-import-indexing ci:web-assistant-state ci:web-settings-state ci:web-db-startup ci:web-destructive-reset ci:web-e2e ci:desktop-smoke ci:desktop-ipc-reset ci:desktop-runtime-hosts ci:desktop-db-storage ci:desktop ci:embedding ci:unit ci:coverage-db ci:coverage-full ci:full
Lane Family What It Covers PR Meaning
Unit / coverage ci:unit, ci:coverage-db, ci:coverage-full Routine app/package changes can run affected unit tests without dragging full coverage. DB/storage/file-system and full-risk changes still get coverage.
Web/product Smoke, file explorer persistence, import/indexing, assistant state, settings state, DB startup, destructive reset, full regression. Product changes should select the exact web behavior they risk, not every web E2E by default.
Desktop Smoke, IPC reset, runtime hosts, DB storage, full regression, embedding diagnostics. Small desktop IPC/reset/host changes should avoid unrelated desktop diagnostics unless risk requires them.
Full release ci:full Workflow, package manager, risk-routing, or broad release-risk changes expand to every relevant lane. This is expensive by design.

Important label timing detail

GitHub evaluates label-gated jobs from the labels present when the workflow starts. If a PR is opened without the selected labels and labels are added seconds later, the initial run may skip the wrong jobs. Prefer creating the PR with labels already attached, or deliberately refresh the PR run after labels are present.

06 / Sentinel

What PR Sentinel Checks

PR Sentinel is the cloud-side auditor. It runs on pull requests, checks out the PR head with enough history, fetches live PR labels, then runs pnpm ci:verify-proof against the actual PR head SHA.

Manifest validity

Schema version, package manager, pnpm version, command results, command durations, owners, budgets, labels, and command coverage must be structurally valid.

Selection consistency

It recomputes risk selection from the base and testedHeadSha, then compares files, risk profile, budget, lanes, labels, and commands.

Tip freshness

It verifies testedHeadSha is an ancestor of PR head and rejects any changed file after proof except the proof file itself.

# What Sentinel effectively does on a PR
pnpm ci:verify-proof \
  --head "$PR_HEAD_SHA" \
  --base "origin/${GITHUB_BASE_REF}" \
  --labels "$PR_LABELS" \
  --github-output "$GITHUB_OUTPUT"
07 / Failures

Common Failure Modes And Fixes

These are the failures new developers are most likely to hit.

Failure Text / Symptom Cause Correct Fix
missing required PR label ci:... The selector required a label that the PR does not have. Add the missing label. If the current run already started without it, refresh the PR run deliberately.
proof is stale: <file> changed after testedHeadSha A source/config/test/doc file changed after the proofed commit. Commit the real change, rerun ci:prove, commit proof-only again, and rerun ci:verify-proof.
testedHeadSha is not an ancestor of head The proof points at a commit that is not in the PR branch history. Regenerate proof from the current branch head.
proof selection does not match recomputed risk selection The risk rules, base branch, files, or selected commands changed since proof was generated. Rerun ci:select, then ci:prove, then commit a new proof-only manifest.
pnpm ci:prove requires a clean worktree You have unstaged or uncommitted files. Commit or intentionally discard the work first. Do not generate proof from a dirty tree.
Label-gated jobs skipped unexpectedly The workflow started before labels were attached, or the selected labels were wrong. Confirm selector output, labels, and latest run. Cancel stale runs and refresh only once labels are correct.
08 / Onboarding

Developer Onboarding Checklist

This is the checklist a new developer should follow before their first Brainstrike PR.

Do

  • Run pnpm ci:select --base origin/main --head HEAD before opening/updating a PR.
  • Read the selected labels and understand why they were selected.
  • Use the selected labels on the PR.
  • Run pnpm ci:prove only from a clean worktree.
  • Commit .ci/proof/latest.json by itself as the final proof-only commit.
  • Run pnpm ci:verify-proof before pushing.
  • Cancel superseded cloud runs after pushing a newer head.

Do Not

  • Do not hand-edit .ci/proof/latest.json.
  • Do not commit source changes after the proof commit and expect it to pass.
  • Do not use full E2E as the default loop just because it feels safer.
  • Do not add broad ci:full labels to avoid thinking about risk.
  • Do not treat stale proof as "close enough".
  • Do not leave failed superseded runs confusing the PR status.

New contributor rule of thumb

If the selector surprises you, stop and inspect the changed files and risk rules. Do not override the lane casually. The selector may be wrong, but the fix is usually a rule/test update, not ignoring it.

09 / Examples

PR Examples Going Forward

The proof system is easiest to understand through examples.

PR Type Likely Selection What The Proof Proves
Documentation-only change No cloud labels, docs/static proof. The diff is clean and does not require expensive product validation.
Regular app/package source change ci:unit, plus product-specific lanes if selectors match. Affected unit tests run without requiring broad coverage by default.
DB/storage/file-system change ci:coverage-db, DB-specific proof commands, possibly browser/data lanes. Data-platform changes still get stronger coverage where regressions are expensive.
Desktop IPC reset change ci:desktop-ipc-reset, desktop unit proof, focused reset/IPC E2E. The reset/IPC surface works without paying for unrelated embedding diagnostics.
Risk-routing or workflow change ci:full. The pipeline itself changed, so the branch must prove every lane contract still works.
10 / Policy

Team Policy Going Forward

The proof system only saves time if the team treats it as operating policy, not a suggestion.

Policy for PR authors

Every PR should arrive with selected labels, fresh local proof, a final proof-only commit, and passing ci:verify-proof. If you make any real change after proof, regenerate proof.

Policy for reviewers

Reviewers should treat missing/stale proof as a process failure, not a nit. Also check that the selected lanes make sense for the touched files.

Policy for CI debugging

Always debug the latest head SHA. Cancel superseded runs. Do not rerun old failed jobs unless they are still attached to the current head and still relevant.

Policy for lane evolution

New product surfaces need risk fixture tests. A lane is not real until positive and negative selector cases prove it selects the right work and avoids unrelated expensive work.

The expensive mistake this prevents

The bad loop is: push vague changes, wait for broad CI, fix one failure, rerun everything, repeat. The proof system forces the branch to state its risk, prove that risk locally, and let CI verify the same claim.
