§1Verdict & headline numbers

This is an unusual codebase: one maintainer orchestrating AI agents at industrial cadence (262 PRs merged in June alone, 1.8% revert/follow-up rate). That reframes what "developer experience" means here. The scarce resources are verification latency, affected-graph precision, and machine-readable conventions, not human onboarding ergonomics. Every recommendation below is scored against those three.

Three facts dominate everything else in this report:

  1. Tests are the only expensive thing in CI, and they are the only thing not cached. Turborepo remote caching is live and working for builds, but test selection was moved off Turbo onto raw pnpm --filter, so every test executes from scratch on every run, including a full 42-minute uncached re-test of the entire repo on every push to main.
  2. A one-line edit to packages/types invalidates the build of 33 of the other 40 packages before a single test runs, because test depends on ^build even though the config's own comment admits tests import source directly.
  3. The entire nightly regression tier has been silently red for 10+ days. Web E2E, desktop E2E, and performance nightlies: 10 of 10 most recent scheduled runs failed, with no failure notification. The "smoke on PR, full regression nightly" strategy is currently fictional on the regression side.

§2How this codebase actually evolves

Evidence base: git log origin/main --since=2026-01-12 --numstat (726 commits, 13,913 file-changes, 1.13M lines ±) and 906 merged PRs via gh pr list. Full method in §9.

The work mix is infrastructure-heavy: db/search/indexing appears in ~39% of PR titles, assistant/agent in ~21%, CI/infra/tests in 14%. Median PR is small and disciplined (345 lines, 6 files, 2 packages), which means affected-based CI filtering is well matched to the modal change. Big work ships as long-lived feature branches carrying stacked PRs (the Turso migration alone: 172 PRs on a side branch), then squash-collapses to main.

The coupling signal: the assistant vertical is welded to apps/desktop

Package co-change analysis (which packages appear in the same commit) is the strongest architectural signal in the history. Filtered to commits touching ≤8 packages (so migration mega-commits don't distort it), the desktop app co-changes with the whole assistant vertical at rates that defeat affected-graph filtering:

Two readings. First: the assistant server (tool registry, hook manager, route handlers, both hidden renderer hosts) lives in app code (apps/desktop/src/assistant-server*), so roughly a fifth of all work dirties the entire desktop app in any affected computation. Second: assistant-contract successfully serializes the process boundary but does not decouple change: 81% of its commits ship in lockstep with both implementer and consumer. Contract packages here buy type safety across IPC/HTTP, not independent evolution. That's fine, but it means more contract packages are not a decoupling strategy for this repo.

The hottest churn chain confirms it. Eight of the sixteen most-committed files are one assistant path: assistant-ui-panel-wrapper.tsx (60 commits) → assistant-ui-panel.tsx (48) → preload.ts (47) → main.ts (45) → assistant-tools.ts (44) → agent/src/index.ts (40) → agent-runtime.ts (38) → assistant-server.ts (31). AGENTS.md itself documents that each new run-lifecycle signal "threads the SAME 5 layers." Every assistant feature pays this wiring tax, twice over once you count the paired test files (another 61 commits).

Two more history facts shape the recommendations: test code is 40% of all line churn (452K of 1.13M lines; live-loop, no-mock proofs are maintained continuously and are the quality backbone behind the 1.8% revert rate), and .github/workflows/test.yml has more commits (61) than any source file in the repo. CI meta-engineering is a recurring first-class work category that already went through one full build-then-delete cycle (the bespoke proof/planner system, 26 commits of .ci/proof/latest.json churn, removed within the window).

§3Package architecture: what's healthy, what's drifting

Evidence base: dependency extraction from all 41 workspace package.json files; DFS cycle check; export-surface and src-file counts; the domain contract in architecture/domain-map.json and its two enforcement scripts.

healthy  The internal graph is a clean DAG with zero cycles, checked across prod, dev, and peer edges. The homegrown domain-boundary system (scripts/architecture-domain-boundaries.mjs, 376 lines: real TS-compiler-API import parsing, per-domain mayDependOn, a ratchet that fails on stale exceptions) currently enforces seven layered domains with boundaryExceptions: []. That is a genuinely rare state of grace and it should be treated as an asset, not replaced (§7).

God packages: the blast-radius problem

Fan-in concentrates in a few leaf packages, and because test and type-check chain through ^build/build, their transitive blast radius is what every edit pays:

  • utils serious  28 direct dependents, 37 export entries, 114 src files. It is not "utils": it contains report-generator (Tapestry product logic per AGENTS.md), workspace-indexing-qos, tree operations, four token-counting entries, the entire pino logging stack, and file-explorer-specific helpers. Domain logic hiding in the highest-fan-in package means product edits invalidate 29 packages.
  • types serious  the inverse: 13 files, mostly file-explorer constants and electron-api.ts, named as the universal leaf. A misnamed file-explorer-contract + platform typings grab-bag with a 33-package blast radius.
  • ui warning  359 src files mixing a generic component library (tree-table, context-menu) with the entire assistant chat surface (assistant-ui-panel, markdown-surface, shiki). The panel is why ui → assistant-contract, commands: every ui consumer (e.g. file-import, which likely needs toasts) drags the chat stack into its graph.
  • preferences warning  two packages fused: persistence stores (data-platform) plus the whole settings feature (src/settings/, settings-page-content.tsx, React components) — the reason a data-platform package depends on ui, and a contributor to its 70% co-change with desktop.
  • app-shell watch  20 internal deps, 200 files. Acceptable as the composition root, but it also owns features (background-indexing sync, context-action registry, run notifications, checkpoint hooks) rather than only wiring them.

Dead weight found along the way: tsconfig.solution.json is stale and referenced by nothing; knip.jsonc still configures a nonexistent packages/fonts; queue-telemetry-collector has zero importers (standalone bin only); server-config's single consumer is apps/web/playwright.config.ts, misfiled as a prod dependency; selection-rules (5 importing files, all in file-explorer-ui) and commands (single export) are merge candidates into their sole consumers.

§4Build mechanics: the hidden tax

Evidence base: per-package build/type-check scripts, both app Vite configs, all 41 vitest configs, turbo.jsonc task graph.

The single most consequential finding of the whole review: the repo maintains a dual dist/src consumption model, and the dist half is mostly dead.

  • Both app bundlers alias every workspace package to source: 43 packages/*/src aliases in apps/web/vite.config.mts, 48 in the desktop one. Unit tests also import source (167 hand-maintained replacement: alias lines across 10+ vitest configs).
  • So for renderer-only packages (app-shell, db-explorer, file-explorer-ui, workspace-search, vector-management, preferences, ui, hooks, …) the built dist/ JavaScript is never executed anywhere. It exists to satisfy Turbo's ^build topology and to emit .d.ts. Only the desktop main process genuinely consumes dist at runtime (its esbuild config externalizes @brainstrike/* to prebuilt bundles), and only for the node-side subset: agent, db, queue, embeddings, utils, worker packages.
  • 18 packages double-compile: tsc -b then tsup over the same sources. Six distinct build patterns and four type-check patterns exist across the workspace (one package, file-explorer, has no type-check script at all).
  • turbo.jsonc's test task declares dependsOn: ["^build"] with its own comment admitting "Unit tests import package source directly." This is the mechanism that turns the §3 blast-radius chart into wall-clock: a types edit rebuilds 33 packages before one test runs.
  • The same knowledge ("which specifier maps to which src") is encoded in four parallel registries: root tsconfig.json paths, two Vite configs, and the vitest alias blocks. Adding one subpath export today touches up to ~14 files.
  • Cache-hygiene detail: globalDependencies includes packages/*/tsconfig*.json, so any of the 75 tsconfig files edits is a global cache bust for all 41 packages.

None of this is exotic to fix, and the canonical shapes are documented (§6, R3/R7). The payoff compounds: smaller ^build graphs make Turbo-cached tests (R2) hit more often, which makes CI cheaper, which makes the 17-PR/day loop faster.

What the measurements say is wrong

  • critical  Dead nightly tier. desktop-e2e, web-e2e, performance: 10/10 recent scheduled runs failed; nightly-coverage 7/10. Only nightly-coverage opens a tracking issue on failure; the other three fail into the void. ~58 min/day of runner time producing zero signal, and the merge gate runs smoke only, so full-regression coverage has been absent for 10+ days.
  • critical  Zero test caching. Test selection deliberately moved off Turbo (a workflow comment cites --affected over-selecting on merge commits) onto pnpm --filter "...[origin/BASE]". Selection semantics were preserved; caching was lost. The remote cache is verified live for builds in the same jobs.
  • serious  The repo builds up to 4× per PR sync (Static's type-check → build, Unit, Coverage, Build): mostly remote-cache replays, but still ~10–14 min of redundant replay plus 4 installs/checkouts. And directly-changed packages' tests run twice (plain in Unit, instrumented in Coverage).
  • serious  Smoke E2E is gated on Unit (needs: [static, unit, build]) but only consumes Build's artifact. A 3.5-minute signal waits 25–54 minutes for a job it doesn't use.
  • warning  Per-job actions/cache turbo silos are near-vestigial next to the live remote cache: keyed per-job-per-sha, they never exact-hit on first run, add save/restore time, and pin cache storage at the 10 GB ceiling (10.26 GB observed, the reason the cleanup workflow exists).
  • warning  Noise and drift: 584 all-skipped claude.yml runs in 38 h (58% of all workflow runs); the checkout→pnpm→node setup block copy-pasted into every job (no composite action: .github/actions/ doesn't exist, and a turbo.jsonc comment references a "shared Playwright runtime setup action" that no longer exists); the same 24-line Electron provisioning block pasted 3× across workflows.
  • warning  Branch protection: required checks are the five test.yml jobs, but strict_required_status_checks_policy: false and 0 required approvals, so stale branches can merge on green-at-old-base. Today's mitigation is the push-time full test run; see R2 and the merge-queue note at the end of §6 for how to keep that safety net while making it cheap.

§6Recommendations, ranked

Ranked by payoff per unit of risk. Each cites the canonical mechanism (official docs, July 2026) rather than bespoke machinery, per your preference, and flags residual risk explicitly. The first chip on each card is its suggested horizon.

R1Resurrect or explicitly retire the nightly regression tier

this weekimpact: signal integrityeffort: smallrisk: none

Three lanes have failed 10/10 consecutive scheduled runs with no notification. Whatever else this review says, this comes first: either fix the regressions (they are your only full-regression coverage; the merge gate is smoke-only) or stop scheduling them until fixed. At minimum, clone nightly-coverage.yml's auto-issue-on-failure block into web-e2e.yml, desktop-e2e.yml, and performance.yml so silent-red is structurally impossible to recur.

Why canonical: this isn't tooling; it's the precondition for trusting every other lane change. A CI tier that can go red for 10 days unnoticed will eat any optimization you build on top of it.

R2Route test execution through Turbo so the remote cache covers it

this weekimpact: highest (latency + cost)effort: smallrisk: managed

Replace pnpm --filter "...[origin/$BASE_REF]" run test with turbo run test --filter="...[origin/$BASE_REF]": the explicit filter keeps your exact selection semantics and sidesteps the merge-commit base-detection issue that pushed you off --affected (alternatively pin TURBO_SCM_BASE). On push, replace test:fast with plain turbo run test: post-merge, nearly every package is a remote-cache hit from the PR that just ran the same content, collapsing the 42-minute push Unit step to minutes while keeping the full-repo safety net that currently justifies merging without strict status checks.

  • The test task is already cache-configured (env-keyed on NODE_ENV/TURBO_TEST_MODE); the remote cache is verified working in the same jobs. You already trust this exact machinery for build.
  • Start with @brainstrike/db pinned "cache": false (known env-sensitive, serialized PGlite lanes) and widen from there. Consider "remoteCache": {"signature": true} + TURBO_REMOTE_CACHE_SIGNATURE_KEY since cached test results now gate merges.
  • Longer term, evaluate --affected with 2.10 semantics (composable with --filter; fails safe by running everything on shallow clones) and turbo query affected for job-level skip decisions, the documented replacements for hand-rolled changed-path detection.
Grounding: Turborepo "Constructing CI" + GitHub Actions guide; 2.10 release notes (composable --affected); remote-caching docs (free on all Vercel plans; self-host seam via turbo login --manual + API v8, e.g. ducktors/turborepo-remote-cache). Residual risk: a test that passes on hidden state could replay a stale green; bounded by input hashing, the db carve-out, and signature verification.

R3Cut the ^build tax: declaration-only builds and no double-compiles

this weekimpact: high (the 33/40 problem)effort: mediumrisk: low

Three moves, in order of safety:

  1. Kill the 18 double-compiles. Each of those packages runs tsc -b and tsup over the same sources. Pick one emitter per package class: tsc-emit for the type-graph, tsup/esbuild only where a real bundle is consumed (desktop main's node-side subset: agent, db, queue, embeddings, utils; and the worker-bundle packages).
  2. Declaration-only builds for renderer-only packages. Their dist JS is never executed (both apps alias to src), so emit .d.ts only. Builds get dramatically cheaper, and the ^build graph that R2's cached tests hash against shrinks.
  3. Narrow test.dependsOn. Tests import source; only worker-bundle consumers (token-cache, chunking-worker, embedding-worker) genuinely need built artifacts. Scope dependsOn accordingly; Turborepo 2.7+ composable config (extends from any workspace package + $TURBO_EXTENDS$) lets you express the exception per-package instead of globally.

Also: standardize the 6 build × 4 type-check × 3 clean script variants behind shared presets in packages/config (it already ships tsconfig presets), give file-explorer its missing type-check script, and stop listing packages/*/tsconfig*.json in globalDependencies once per-package task inputs cover them; today any of 75 tsconfig edits busts every cache in the repo.

Grounding: Turborepo's official TypeScript guide recommends per-package tsc --noEmit check tasks under turbo (explicitly not project references); your shape already matches; this makes the build side match too. Payoff compounds with R2: smaller build graphs → more cache hits → faster lanes.
Correction — 2026-07-15

Series B's build-mechanics audit (#1650, #1649, #1651, #1652, #1658) found the "18 packages double-compile" premise above overstated: it was double parse, not double compile — every package already set emitDeclarationOnly, and tsup was always the sole JS emitter. Because desktop main executes dist at runtime by design, declaration-only builds were dropped as a goal rather than pursued. Separately, "tests import source directly" (the premise behind narrowing test.dependsOn) was false for 13 of 18 packages until #1651 made it true via a src-alias registry and execution guard. The series still landed real wins — script hygiene, globalDependencies narrowing, a Unit phase split, and a topo transit node that collapsed the whole-repo test graph from 39 build tasks to 3 — just not the ones this recommendation predicted.

R4Ungate smoke E2E from Unit

this weekimpact: PR latencyeffort: one linerisk: trivial

Change both smoke jobs from needs: [static, unit, build] to needs: [build] (or [static, build] if you want a cheap sanity gate). The e2e pair consumes only Build's artifact; today a 3.5-minute signal waits behind Unit's 25–54 minutes. Combined with R2, merge-readiness becomes max(Static, Unit) rather than a serial chain.

Cost of being wrong: ~2–3 wasted e2e minutes on PRs whose Unit fails anyway (~9 fails + 40 cancels per 136 runs), trivial against Unit's cost.

R5Extract packages/assistant-server out of apps/desktop

this monthimpact: high (affected-graph precision)effort: medium-largerisk: churn during move

The single highest-payoff structural move. 60–70% of all agent and preferences commits also touch apps/desktop, and the hottest churn chain (assistant-tools.ts, assistant-server.ts, the IPC domain handlers, both hidden host managers) lives in app code. Moving the assistant server (tool registry, hook manager, route handlers) into a package:

  • shrinks the affected graph for ~21% of all work (assistant changes stop dirtying the whole desktop app, so R2's caching and any affected filtering actually bite);
  • makes the server testable without desktop scaffolding (today's paired tests live in apps/desktop/__tests__);
  • creates the natural home to collapse the "adding a native tool is a 7-registry checklist" (schemas, contract registries ×4, live registry, default-instructions) into fewer, co-located registration points; every "register in BOTH places" instruction in AGENTS.md is a defect attractor at 17 PRs/day (the dual lane-registry incident #1101 is the same pattern).

While in there, flatten the panel-prop pipeline: assistant-ui-panel-wrapper.tsx (60 commits) threads each new run-lifecycle signal through the same 5 layers. A context/event-bus seam for run-lifecycle signals would cut the hottest non-config churn site in the repo.

Grounding: your own history data; this is the review's clearest case of "structure should follow measured change patterns," not ecosystem fashion.

R6One module-resolution registry instead of four

this monthimpact: DX + drift eliminationeffort: small-mediumrisk: low

Root tsconfig.json paths, two Vite configs (43 + 48 aliases), and ~167 vitest alias lines all encode the same mapping. Make the tsconfig the single source: vite-tsconfig-paths in both apps, and vitest configs consuming the same plugin or a single generated alias module from test-utils. Adding a subpath export becomes a one-file change instead of ~14. Delete tsconfig.solution.json (stale, unreferenced) and the knip.jsonc packages/fonts entry while you're there.

Why canonical: tsconfig paths is the ecosystem's shared source of truth; every bundler/test-runner has a first-party or de-facto standard adapter for it. Hand-synced alias blocks are the bespoke thing.

R7Demote the Coverage lane from every-sync to on-demand

this monthimpact: ~25% of PR pipeline costeffort: smallrisk: feedback loss

Coverage is advisory (not in the ruleset), re-executes changed packages' tests in instrumented form, and costs 11–14 min per sync. Move it to ready_for_review + a label, or nightly (nightly-coverage already exists and enforces thresholds). If per-PR patch coverage matters for review, run it once per PR lifecycle rather than per sync.

Correction — 2026-07-15

The "11–14 min per sync" figure above was overstated: measured Coverage runs are 5–9.5 min. The mechanism (per-sync waste on an advisory lane) was right; the magnitude wasn't. #1664 moved Coverage to its own once-per-lifecycle workflow; measured across 5 sample PRs, that collapsed 21 coverage runs to 5.

R8Adopt pnpm catalogs; retire syncpack

this monthimpact: dependency hygieneeffort: smallrisk: low

Catalogs (catalog: protocol in pnpm-workspace.yaml) are the canonical single-source for dependency versions, with catalogMode: strict to reject drift and cleanupUnusedCatalogs. Turborepo's lockfile analysis understands catalogs, so a catalog bump only cache-misses affected packages. This replaces syncpack's job with a native mechanism, and Renovate has first-class catalog support. Also audit pnpm 11's on-by-default supply-chain settings (minimumReleaseAge: 1440, blockExoticSubdeps, trustPolicy): your workspace file already carries a documented minimumReleaseAgeExclude, which is exactly the right pattern; confirm the umbrella settings weren't disabled during the v11 migration.

Grounding: pnpm catalogs + settings docs; pnpm 11.0 release post; Turborepo 2.7 notes (catalog-aware hashing).
Correction — 2026-07-15

"catalogMode: strict to reject drift" doesn't do what the name implies: pnpm's strict mode does not reject a hand-edited literal version for a catalogued dependency. pnpm install exits 0 and silently resolves a second, parallel version. Only pnpm add <pkg>@<off-catalog-version> is rejected. #1669 ships the real enforcement, scripts/verify-catalog-references.mjs in the Static job, a check syncpack never had since it was never wired into CI.

R9Workflow hygiene: composite setup action, cache re-key, event pruning, ARM runners

this monthimpact: cost + drifteffort: smallrisk: low

  • Drop or re-key the actions/cache .turbo layer: with remote cache live it's near-vestigial; if kept as an outage hedge, key on lockfile+turbo.jsonc hash (performance.yml already does this) instead of per-job-per-sha, which is what pins storage at the 10 GB ceiling.

  • Make lint cacheable per-package (Biome is file-local and deterministic on inputs; the eslint invocation targets 4 fixed dirs, so key on them), keeping only genuinely repo-global checks (secret scan, contracts) uncached. This attacks Static's fixed 8–13 min floor.

Correction — 2026-07-15

Lint-cache prize. "Static's fixed 8–13 min floor" was overstated: measured Static total is ~197s on typical pushes, and Lint itself is ~91s of that. The 8m+ figures were cold whole-repo-invalidation runs, not the steady state. 6 of lint:ci's 8 chained commands are inherently whole-repo scanners, so lint caching was deferred; the realistic prize is ~40–60s on a cache hit, not minutes.

ARM runners. #1670 measured Static at 2.7–3.0 min on ubuntu-24.04-arm vs. 2.9–3.1 min on x64: parity, not a speedup. The win is purely the 37% cheaper per-minute rate. Also, turbo's cache key is architecture-agnostic (the hash omits CPU arch; runner.os reports "Linux" on both), and the remote cache replays x64-produced results on ARM runners, so ARM buys the rate discount, not independent per-arch validation. Recorded in docs/agents/ci-quality.md.

R12Modernization audit: TS7 lane, Turbo 3.0 deprecations, boundaries-advisory

this quarterimpact: future-proofing + speedeffort: small to evaluaterisk: ecosystem timing
  • TypeScript 7 (Go-native) went GA 2026-07-08 with 8–12× type-check speedups and structurally identical semantics. Your type-check lanes are pure CLI tsc --noEmit: the ideal early adopter surface. Caveat: 7.0 ships no programmatic API until 7.1, so anything consuming the TS API (typescript-eslint et al.) stays on 6.x; per-lane adoption, not a repo-wide switch. Static's 5.5-minute type-check step is the prize.
  • Turbo 3.0 prep: audit for deprecated idioms now (--parallel, TURBO_REMOTE_ONLY, turbo-ignore, --no-cache), and note 2.10's native cacheMaxAge/cacheMaxSize local-cache eviction, which can replace the 25 GB LRU pruning half of scripts/run-turbo-command.mjs.
  • turbo boundaries is still experimental (RFC open since 2.4). Adopt it in advisory mode for its two native checks (out-of-package imports, undeclared dependencies; the latter is a check nothing else in your stack does) and a first tag taxonomy. Do not retire the homegrown domain script for it (§7).
Grounding: TS 7.0 GA announcement; Turborepo 2.9/2.10 release notes; boundaries reference (marked experimental). All fetched July 2026.
Correction — 2026-07-15

#1666's parity check found TS7 adoption blocked, not merely "an early-adopter surface": 64 of 67 type-check invocations match byte-for-byte, but apps/desktop/tsconfig.main.json's moduleResolution: "node" is a removed option under TS7, and the paired fix (module/moduleResolution: Node16) produces 88 errors under both compilers. Adoption is blocked on a full CJS→ESM migration of the Electron main process, not a TS7-side gap. Findings plus a re-runnable parity guard are in docs/series-c-ts7-parity-findings.md.

Considered and deliberately deferred: merge queue

With strict_required_status_checks_policy: false and ~27 pushes/day, stale-base merges land semantically untested: the textbook merge-queue case (merge_group trigger + required checks is the canonical protection for busy repos). But a queue multiplies CI runs at exactly the volume where you're trying to cut spend, and R2 makes the existing mitigation (full post-merge test run + fast revert culture) nearly free. Defer, with a tripwire: if red-main incidents recur after R1/R2 land, adopt the queue and let the cached lanes absorb the extra runs.

§7What not to change

A defensible review names what's working, because an independent reviewer should push back if these get "modernized" away:

  • The homegrown domain-boundary system. Real compiler-API import analysis, a ratchet on stale exceptions, and a current state of zero violations. The canonical alternatives don't beat it: turbo boundaries is experimental with a coarser rule vocabulary; eslint-plugin-boundaries would reintroduce an ESLint toolchain into a Biome-first repo. If the script ever outgrows itself, the canonical landing spot is dependency-cruiser: declarative, maintained, testable. Until then: keep, and tighten the domain map as R10 splits land.
  • Per-package Vitest under Turbo. Vitest 4 removed workspace files in favor of root projects, but Turborepo's own Vitest guide explicitly favors per-package test tasks for caching; a root-projects config makes any change a global cache miss. Your shape is the documented canonical one; R2 is what makes it pay.
  • The db lane registries. Serialized PGlite lanes do something Turbo can't (intra-package test partitioning), and the Static-job guard on both registries is a good defect trap. The improvement is generation, not removal: derive coverage-lanes.mjs from test-lanes.mjs so the "register in BOTH" footgun (#1101) becomes structurally impossible.
  • The stacked-branch delivery pattern. 172-PR migrations with a 1.8% revert rate is a working system. R2's cheap push-runs and R1's restored nightlies protect it; nothing here should add per-PR ceremony.
  • Capability-injection over isElectron(). The pattern is sound; the §2 web↔desktop coupling is about duplicated composition roots, not the gating idiom. A shared platform-composition seam is worth exploring after R5, not before.
  • Contract packages, at current count. They serialize process boundaries well. Just don't add more expecting decoupling; the history data (81% lockstep) says that's not what they buy here.
Status — 2026-07-15

#1663 verified the "db lane registries" recommendation above was already implemented: both coverage-lanes.mjs and test-lanes.mjs import one shared db-test-lane-manifest.mjs, so coverage lane assignment is automatic and the "register in BOTH" footgun this bullet worried about no longer exists. The PR's job became verification plus a doc correction, not new code.

The compounding argument

These aren't twelve independent chores. R3 shrinks the build graph → R2's cache hits more often → PR and push lanes get faster → the 17-PR/day agent loop tightens → R5/R10's structural splits make the affected graph more precise → cache hits improve again. The order above is chosen so each step lowers the cost of the next.

§9Method, confidence & sources

What was measured vs. estimated

  • Measured: dependency graph and cycle check (all 41 package.json files); build/type-check script inventory; alias-line counts; churn and coupling (726 main commits, numstat, rename-resolved, package = first two path segments); PR statistics (906 merged PRs via gh, #564–#1604); CI durations and failure rates (1,000 runs ≈ 38 h window); ruleset 4797672; job-minute anatomy from named runs (29178469954, 29176448480); cache storage (10.26 GB / 20 caches); remote-cache liveness (observed hits in Build job logs).
  • Estimated (marked as such in place): post-change lane durations, monthly job-minute extrapolation and dollar figures, coupling-to-affected-savings mapping for R5. The 38-hour observation window is high-volume but short; durations are medians of that window, not long-run averages.
  • Known limits: title-keyword PR classification is overlapping and approximate; co-change coupling was computed both raw and filtered (≤8-package commits) with stable rankings; nightly failure count is "last 10 scheduled runs" per lane as of 2026-07-12.
