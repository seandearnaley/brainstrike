The engine layer is already in good shape: transaction-scoped HNSW tuning, 250-row batched upserts, a SKIP LOCKED lease queue, a priority scheduler protecting the single connection, and the BM25 lexical arm are all solid, benchmark-backed work. The highest-impact items left are finishing two fixes that already exist (one unmerged, one applied to only one of two code paths), compensating for what single-process Postgres never does on its own (ANALYZE), and a measured engine-tuning pass — every global GUC still sits at stock server defaults that assume spinning disks and 100 concurrent backends. The best product win is free: a hybrid BM25+vector assistant tool is fully built and registered nowhere.

1Merge the filtered-search exact-scan routing fix

PerformanceHigh — measuredEffort S

The single biggest search-quality problem at scale is already solved — but at audit time the fix lived only on an unmerged local branch (verified via git merge-base: not an ancestor of main). Main has no resolveFilteredVectorSearchRoute: every filtered vector search (any filter beyond embedding_set_id) goes through HNSW, whose post-filter recall collapses on narrow subsets. Status: now open as PR #1706 (the 2026-07-11 fix cherry-picked onto current main, full db suite green).

HNSW post-filter (today)
39.8% recall@10 · 84.8ms p50
adaptive exact routing
100% recall@10 · ~80–94ms p50

Benchmarked 2026-07-11 at 100k chunks × 1024 dims, production query shape. Alternatives (hnsw.max_scan_tuples, per-root partial indexes) were measured and rejected.

Action

Done — PR #1706. The fix ships adaptive routing in both FileChunkRepository and ElectronFileChunkRepository: bounded selectivity counts route narrow searches (≤20k matched AND ≤15% of set) to an exact fp32 scan. Count overhead measured at ~4–14ms; whole-set searches never pay it.

2Apply the 512MB index-build fix to the desktop rebuild lane

Perf + MemoryHigh — measured 5×Effort S

PR #1584 landed the maintenance_work_mem sizing fix (64MB → up to 512MB, clamped for 32-bit WASM) in createDimensionIndex — but the desktop idle-maintenance scheduler has its own SQL builder that never got it. createDimensionIndexSql (apps/desktop/src/dimension-index-maintenance-scheduler.ts:141–175) emits a bare CREATE INDEX … USING hnsw through db.maintenance.exec with no SET / RESET maintenance_work_mem. Every scheduler-driven rebuild runs at the 64MB default.

64MB (scheduler today)
2,496s — DB blocked
512MB (helpers path)
505s

HNSW build, 100k chunks × 1024 dims (halfvec). The build blocks every other query on the single connection — this is 42 minutes vs 8.5 minutes of frozen DB.

Action
  • Route the scheduler through createDimensionIndex (which already sizes, sets, and — critically — RESETs the GUC in a finally), or wrap its exec with the same SET/RESET pair on the maintenance channel.
  • While there: the 'concurrent' strategy emits CREATE INDEX CONCURRENTLY. On a single-connection engine nothing can run concurrently anyway — the statement still occupies the only connection while doing extra table scans. Verify and likely remove that branch.

Status: PR #1707 (verified: the 'concurrent' strategy is unreachable in production wiring — removal is a separate follow-up).

3Scheduled ANALYZE — nothing maintains planner statistics

PerformanceHigh — verified gapEffort S

Measured on a fresh instance: pg_stat_activity shows exactly one standalone backend. There is no autovacuum launcher (the autovacuum=on GUC is inert), so column statistics are only ever collected when something runs ANALYZE — and almost nothing does. The full runtime inventory: scheduled maintenance VACUUMs job_queue only (every 10 min, idle-gated); the embedding backfill VACUUMs file_chunks once post-drain (plain VACUUM — updates row counts, not column histograms); the token cache runs ANALYZE file_token_cache after bulk deletes. file_chunks, file_records, and embedding_cache can go from 0 to 100k+ rows with the planner still holding empty-table statistics.

Stale stats directly threaten the paths that matter: grep-candidate JOIN ordering (file_chunks ⋈ file_records ⋈ roots), tsvector/BM25 candidate estimates, the dedupe CTEs, and — once #1 merges — the selectivity counts that drive exact-scan routing.

Action
  • Add ANALYZE targets (file_chunks, file_records, embedding_cache, job_queue) to scheduled-database-maintenance.ts — it already has the idle-gating, table-name validation, and priority plumbing.
  • Upgrade the post-backfill VACUUM file_chunks to VACUUM (ANALYZE) file_chunks, and run ANALYZE after bulk imports complete.
  • Cheap insurance: ANALYZE on 100k rows is seconds, runs at background priority, and prevents silent plan regressions that would otherwise be diagnosed one mystery at a time.

4Wire the already-built hybrid search tool into the assistant

ProductHigh — built, unwiredEffort S–M

The Explorer search panel gets hybrid BM25+vector retrieval with RRF fusion. The assistant does not: brainstrike.queryEmbeddingSpace is pure vector cosine. Meanwhile packages/agent/src/tools/hybrid-search-tool.ts defines a complete brainstrike.hybridSearch tool and buildToolsWithHybridSearch — with zero call sites. The desktop assistant registry (assistant-tools.ts) never registers it. All the hard parts (BM25 index, migration 053, RRF, eval gates) shipped; the agent just can't reach them.

Action
  • Register the hybrid tool in the assistant tool registry (or swap queryEmbeddingSpace's internals to the hybrid service with a mode flag), respecting the same rootIds scoping the Explorer path pins.
  • Close the eval gap while at it: eval:retrieval scores the vector arm and lexical arm in isolation — nothing scores the fused ranking. Add a hybrid/RRF golden set so fusion quality is pinned the same way the arms are.

5Engine tuning pass: work_mem, random_page_cost, shared_buffers

Perf + MemoryMedium–High — benchmark-gatedEffort M

Outside HNSW search tuning and the per-build maintenance memory, every global GUC sits at stock Postgres defaults — defaults written for a shared server with spinning disks and 100 backends, not a single-user embedded engine. Measured on PGlite 0.5.4 (full table in §3):

  • work_mem = 4MB — every sort/hash spills past 4MB to temp files. Vector search overfetches up to 10,000 rows before sorting; GIN searches (trgm, tsvector) build bitmaps; the grep path sorts ORDER BY path, chunk_index. One user, one connection: there is no multi-backend multiplication risk. SET work_mem = '32MB' at connection open is a classic embedded-DB win — benchmark 16/32/64MB with the existing harness.
  • random_page_cost = 4.0 — a spinning-rust number. Browser storage is an in-memory MEMFS mirror (RAM-speed reads); desktop is NVMe. The planner is being told random I/O costs 4× sequential, biasing it away from index scans exactly where index scans are nearly free. SET random_page_cost = 1.1 is the standard SSD/RAM setting.
  • shared_buffers = 128MB — allocated inside the WASM heap of every instance, including browser tabs. Verified: ALTER SYSTEM SET shared_buffers works in PGlite and persists to postgresql.auto.conf (applies on next open). Consider 64MB for browser profiles (smaller tab footprint; MEMFS makes OS-cache arguments moot) and leaving/raising desktop. Restart-scoped, so apply during init before migrations.
  • Confirmed non-levers, so nobody chases them later: jit = on but pg_jit_available() = false (inert in WASM); fsync = off at the Postgres layer by design — durability lives in the VFS syncToFs contract, so WAL-tuning GUCs have limited reach; parallel workers are 0 (no bgworkers).
Action

Add a small session preamble (work_mem, random_page_cost) at all four construction sites plus the desktop host, gated behind one shared helper; benchmark before/after with the existing vector + FTS harnesses at 100k scale. Spike ALTER SYSTEM for shared_buffers per platform. Keep the NO-FALLBACKS rule: the helper throws if a SET fails.

6Collapse the job-queue polling storm

PerformanceMediumEffort M

Three independent timers poll the queue during indexing, all funneling into the one connection while the embedding pipeline is trying to use it:

  • indexing-activity-coordinator.tsx — every 1000ms, a 5-way COUNT(*) FILTER + MIN(run_at) aggregate over job_queue, plus a second 1000ms poll of collection stats.
  • embedding-job-queue-tracker.tsx — every 1500ms, getQueueStats() = 3 sequential queries (state group-by, metrics select, MIN group-by).
  • use-pending-chunks.ts — every 2000ms, SELECT dedupe_key FROM job_queue WHERE state IN ('queued','running').

That's ~6 queries/sec of aggregate scans against the churn-heaviest table in the schema (every job row is UPDATEd multiple times through its lease lifecycle, so dead-tuple density between 10-minute vacuums makes those COUNTs progressively more expensive — precisely when the user is watching progress).

Action
  • Fold getQueueStats's 3 queries into one statement (they're all single-table aggregates).
  • Consolidate the three consumers onto one shared snapshot poller (the BST-359 tracker comment already points this direction), or convert to live queries keyed on the denormalized job_queue_metrics / collection_indexing_stats tables instead of counting the queue itself.

7Serve coverage/status UI from denormalized stats

PerformanceMediumEffort M

Two live-query hooks aggregate over the big tables on every refresh: use-collection-embedding-coverage.ts (COUNT(DISTINCT fr.id) / COUNT(fc.id) over file_records LEFT JOIN file_chunks) and use-file-collection-status.ts (same join shape). They're set-scoped, but at 100k chunks each refresh re-scans the active set's chunks — and live-query refreshes fire on exactly the tables the indexing pipeline is hammering. The codebase already has the right pattern: use-document-count.ts reads the denormalized collection_indexing_stats table instead.

Action

Extend collection_indexing_stats (or a sibling) with the coverage columns those two hooks need, maintained where chunk/embedding writes already update stats, and point the hooks at it. Aggregate-on-write once beats aggregate-on-read per refresh.

8GIN pending-list policy for smoother ingest

PerformanceMedium — hypothesis, benchmark firstEffort M

file_chunks carries three content indexes — BM25 (25MB @ 50k chunks), trigram GIN (17MB), tsvector GIN (8.6MB) — that together are ~82% of the table's index bytes and are all maintained on every insert. The two GIN indexes use fastupdate=on with gin_pending_list_limit = 4MB (measured default). In stock Postgres, autovacuum merges the pending list in the background; here there is no autovacuum, so the merge happens inline on whichever unlucky INSERT overflows the list — a periodic latency spike in the middle of bulk ingest, on the single connection.

Action

Benchmark two policies at 100k-chunk ingest: (a) fastupdate=off on both GIN indexes (pay a small constant cost per insert, never spike), vs (b) keep fastupdate and add gin_clean_pending_list() to the idle maintenance pass. Measure p99 insert latency, not throughput — the spike is the product problem (frozen UI beat), not the average.

9Ship the index-consolidation migration (+1 newly found duplicate)

MemoryLow–MedEffort S

The skip-scan audit's three DROP verdicts (idx_embedding_cache_content_hash, idx_file_token_cache_lookup, idx_file_token_cache_folder — ~2.6MiB at seed scale, growing linearly, plus write amplification on two hot cache tables) are still sitting in an unregistered draft: docs/pg18-index-consolidation.draft.ts, marked “Do not import.” This audit also found a fourth: the live schema defines both idx_prompt_item_revisions_unique (UNIQUE) and idx_prompt_item_revisions_item_revision on the same (prompt_item_id, revision) columns (schema/index.ts:342–345) — a straight duplicate pair.

Action

Done — PR #1709 (migration 060, all four drops, dual-registered). At 500k cached embeddings the content_hash drop alone is ~25MB.

10Full-text search micro-optimizations

PerformanceLow–MedEffort S
  • BM25 rank computed twice per candidate row. fullTextSearch emits -(content <@> to_bm25query(...)) in both the projection and the ROW_NUMBER() window (file-chunk-repository.ts:601,607). Check with EXPLAIN VERBOSE whether the planner de-duplicates it; if not, compute once in a subquery and rank over the alias.
  • ts_headline runs over the whole candidate pool. Headline generation re-parses each document; with includeHeadline defaulting true it runs for every row in the ftsLimit pool, not the returned page. The hybrid path already opts out — restrict headline computation to the final page for the remaining callers.

11Reconcile the two migration runners' index sets

IntegrityMedium — strategicEffort M

The numbered MigrationRunner (tests) and the Drizzle ledger (the real app) materialize different schemas. Tests run with ~17 indexes the app never gets (extra file_chunks, job_queue, and file_records indexes), and one divergence is semantic, not cosmetic: tests enforce queue dedupe with a UNIQUE partial index (idx_job_queue_dedupe_active) while the app has a plain index and relies on the enqueue CTE alone. Every plan-shaped test conclusion and any uniqueness-race assumption is being validated against a schema production doesn't have.

Action

Decide the canonical index set per table (the skip-scan audit's inventory is the map), align the numbered path to the drizzle baseline (or vice versa), and add a parity test that diffs pg_indexes between the two runners so this can't silently drift again — the same structural fix that killed the dual-registry drift for test lanes.

12Transaction-wrap assistant message persistence

IntegrityLowEffort S

PgliteMemoryStore.saveMessages issues two autocommit statements — the message upsert, then the thread updatedAt bump (memory-store.ts:859,889). A crash between them leaves messages whose thread ordering timestamp lags. Wrapping both in one transaction closes the window and halves the scheduler dispatches per save. Small, but it's the chat hot path. Status: PR #1708.

13Capability menu — interesting things the engine can already do

ProductIdeas — pick opportunistically

33 contrib extensions ship on disk inside the PGlite dist; the app loads one (pg_trgm). The interesting unused surface, roughly ordered by product value:

  • Database perf HUD — pg_stat_statements and auto_explain are both in the dist. A db-explorer “engine health” panel (top statements, slow-plan log, table/index sizes via pg_relation_size) would make every future optimization data-driven instead of audit-driven. Spike needed: pg_stat_statements normally requires shared_preload_libraries — verify loadability in PGlite first.
  • Usage analytics over data you already collect — brainstrike_assistant_run_usage has per-run tokens, cost, provider, model, root. Only a cross-root SUM rollup reads it. A date_trunc time-series (cost/day, tokens/model) as a live-query dashboard — and as an assistant-queryable tool (“what did I spend this week?”) — is a few queries away. Watch the known gotcha: PGlite returns bigint aggregates as strings.
  • unaccent — diacritic-insensitive full-text search; chains into the existing tsconfig.
  • fuzzystrmatch — Levenshtein/soundex for typo-tolerant quick-open and findWorkspaceSymbol, complementing trigram (which needs 3-char literals).
  • PG18 features on the shelf — virtual generated columns (034 uses STORED; virtual = zero storage for derived columns), temporal WITHOUT OVERLAPS constraints, RETURNING new.* (only old.* used so far, in the prompt-revision CAS — a nice pattern worth reusing for other optimistic-concurrency writes).
  • pgcrypto — available if at-rest field encryption is ever wanted for sensitive columns.
