# Database and catalog boundaries

## Desktop ownership

The existing agent-host StateStore owns canonical roots, source records, model
choices, collections, prompts, groups, presets and worktree metadata. The committed
host log owns conversations, runs, decisions, usage and workspace bindings.
Derived indexes are separate owners. Desktop does not construct PGlite or expose
a renderer SQL/live-query compatibility bridge.

Both desktop-first and CLI-first clients borrow the catalog through the same
authenticated host attachment. Authenticate before registering catalog endpoints;
drain admitted operations before retiring their writer. This grants no additional
desktop credential or MCP privilege. Root descriptors carry canonical identity;
renderer paths do not establish ownership.

## Catalog and schema

The provider catalog is the source of static model metadata; user choices are
separate. Keep its runtime schema, supported consumers and current-schema creation
consistent. Surviving PGlite catalog changes edit the current-schema DDL and its
ledger key; the Drizzle ledger is derived. Do not invent legacy-data conversion
or populated old-schema gates: [ADR-0020](../adr/0020-greenfield-data-lifecycle.md)
governs greenfield scope.

Updating only the static catalog is NOT enough — the in-app model picker is driven
by a DB-backed catalog, so a catalog change is a two-part edit. The single source
of truth to edit is:

   - packages/assistant-contract/src/provider-catalog.json

The catalog is DATA, not a TypeScript literal.
`scripts/provider-catalog-key-order-guard.mjs` and the provider env-keys mirror contract read it with `JSON.parse`,
so no catalog field may reference a constant; comments are optional `_note`
strings that `parseProviderCatalog` strips. `tsc` does not check catalog rows,
because JSON widens under `resolveJsonModule`:
`packages/assistant-contract/src/provider-catalog-schema.ts` does, at module load, and THROWS.
Every object is a Zod `strictObject`, so an unknown or misspelled key fails
rather than being dropped, and adding or retyping a field means editing the
schema AND the interface in the same change. Catalog row changes that must
survive in PGlite land in the current-schema DDL, by regenerating it.

### Schema construction is ONE step

`packages/db/src/migrations/current-schema-ddl.ts` is the whole schema in one
step, and it is what production applies at boot, as the single entry in the
migration registry (`001-current-schema.ts`). It replaced a 151-migration
incremental chain whose only remaining job was to arrive at this schema; ADR-0020
is why that history is not worth replaying.

It is GENERATED by reading the catalogs of a booted database (`pnpm --filter
@brainstrike/db db:schema:ddl`), never transcribed from source, because Postgres
normalizes as it applies DDL. Regeneration is a ROUND TRIP -- apply, read back,
re-emit -- and a correct DDL is a FIXED POINT of it, so the command is safe to
run at any time and a non-canonical hand edit shows up as a diff. It is
TypeScript rather than `.sql` because it is on the browser boot path: `packages/db`
compiles with plain `tsc` and ships `dist/`, so a `.sql` file is never emitted
and could not be read without `node:fs`.

`CURRENT_SCHEMA_LEDGER_KEY` is the sha256 of the DDL text, so changing the
schema changes the ledger identity automatically and
`assertNoStaleDrizzleMigrationLedger` makes an already-built profile fail to open
rather than silently stay on a schema this build no longer ships. There is no
`down`: ADR-0020 does not build rollback, and `MigrationRunner.rollback` refuses.

A SCHEMA CHANGE is authored IN THE DDL. `current-schema-ddl.ts` is the source of
truth for what the database contains, so:

1. Edit `src/migrations/current-schema-ddl.ts` -- add the column, table, index
   or seed row there.
2. Run `pnpm --filter @brainstrike/db db:schema:ddl`. This NORMALIZES what you
   wrote (boot, read the catalogs back, re-emit), so `VARCHAR(64)` comes back as
   `character varying(64)`, and it re-derives the ledger key from the new text.
3. Run `pnpm --filter @brainstrike/db db:schema:catalog` to regenerate
   `__tests__/fixtures/schema-catalog.snapshot.txt`.
4. Update `src/schema/index.ts` as well **if** drizzle's typed query building
   needs to see the change.

Both regenerated files belong in the same commit, and the snapshot diff is the
review surface for what moved.

Step 4 is SEPARATE and does not drive step 1. Editing `src/schema/index.ts`
alone changes nothing about the shipped schema: that file is the deliberately
drifted drizzle model (see the "SNAPSHOT DRIFT (intentional)" sentries) and
`db:generate` is blocked, so there is no path from it to the DDL. Running
`db:schema:ddl` after editing only that file is a NO-OP -- the generator boots
the existing DDL and re-emits it unchanged. This mirrors the pre-collapse rule,
where a numbered migration created the table and `src/schema/index.ts` described
it for drizzle; only the authoring file changed.

The schema is held to that frozen snapshot by
`__tests__/current-schema-catalog.integration.test.ts`, which boots production
from initdb and compares catalog readback: relations, columns, constraints,
indexes with their access methods and parameters, sequences, extensions,
generated columns, row counts, and the seeded catalog rows. The snapshot's
content is the output of the REAL 151-step chain, captured before it was
deleted, so that comparison is a standing equivalence proof and not a
self-comparison. The only values exempted from the row comparison are columns
whose DEFAULT is non-IMMUTABLE per `pg_proc` (the clock, `uuidv7()`); the seed
leaves those to fire at install time.

### An artifact derived from itself cannot be the source of anything it has lost

`current-schema-ddl.ts` is authored BY HAND and normalized by the generator. The
generator introspects whatever `migrate()` built -- which is this DDL -- so it
can only ever re-emit what the file already says. Two defects in this work came
from forgetting that, and both looked like something else at first:

- The collapse dropped migration 074's `REVOKE EXECUTE ... FROM PUBLIC` on
  `pg_sleep*` and `set_config`. Re-running the generator could not bring them
  back; it emitted `FUNCTION PRIVILEGES: none`, because the database it read had
  already lost them. The DDL and the fixture had to be regenerated FROM THE
  CHAIN, in a worktree at the commit that still had it.
- The first documented workflow said a schema change edits `src/schema/index.ts`
  and then regenerates. That is a no-op: nothing in the drizzle model reaches
  the generator.

So: when a derived artifact is wrong, the fix comes from OUTSIDE it. Reach for
the independent source -- the chain in git history, or your own hands on the DDL
-- never for "just regenerate it".

### The comparison's coverage boundary is enforced, not assumed

A catalog comparison is only as good as the classes it reads, and "no diff" is
easy to misread as "nothing changed" when it means "nothing changed in what I
looked at". The `pg_sleep` regression passed a zero-diff proof for exactly that
reason.

So the boundary is stated in both directions:

- **COMPARED**, by `current-schema-catalog.integration.test.ts` against the
  frozen fixture: extensions, enum and domain types, relations, columns,
  constraints, indexes, sequences, views, triggers, routines, comments, function
  privileges, relation PUBLIC privileges, row counts and seed rows.
- **ASSERTED TO ADD NOTHING**, by
  `schema-coverage-boundary.integration.test.ts`, which diffs the shipped
  database against a pristine one carrying the same extensions: access methods,
  casts, collations, default privileges, event triggers, extended statistics,
  foreign servers, operator classes, operators, publications, RLS policies, role
  settings, roles, rules, schema PUBLIC access, schemas, security labels,
  standalone composite/range types, subscriptions, table inheritance,
  tablespaces, text search configs and dictionaries.

Identity against pristine rather than literal emptiness, because `pg_cast` ships
258 rows and `pg_operator` 855; identity subsumes emptiness for the classes that
are empty and still catches an addition in the ones that are not.

Adding an RLS policy, a role, a default ACL or a custom type therefore FAILS that
test. That is the point: whoever adds one must either extend the dump in
`src/schema-snapshot/introspect.ts` to compare it properly and regenerate the
fixture, or record why it needs no comparison. Do not widen the asserted-empty
list to make a red run green.

The drizzle-kit artifacts are NOT on the boot path. `drizzle/meta/`'s snapshot is
deliberately drifted from `src/schema/index.ts` and `db:generate` is blocked, so
drizzle-kit emits nothing production applies; `src/drizzle/migrations.json`
survives only as the drift projections
`src/architecture/db-migration-authority.ts` audits, and that module is now its
only reader.

## Remaining PGlite consumers

Web and explicit test/conformance paths retain PGlite. Each construction loads the
shared qualified engine extensions, with live-query support only where required.
Keep the engine family compatible through its existing package catalog and
compatibility check; a partial version change must not bypass that check.

PGlite is one connection. Admit multi-statement operations through its existing
scheduler/atomic transaction primitive. Drain statements and live subscriptions
before close, reset or replacement. `statement_timeout` does not bound WASM work;
neither a timer nor an AbortSignal proves a synchronous statement stopped. A
poisoned engine fails visibly and is not repeatedly reopened.

Browser first-run bootstrap applies only to a missing store. It becomes complete
only after the strict persistent instance's awaited flush and existence check;
interrupted-bootstrap cleanup cannot delete a completed user store.

## Data loss boundaries

Durability classification determines repair and export policy. Precious state and
schema ledgers are never automatically truncated; derived data needs a real
rebuild owner. A cascade must not turn derived repair into canonical data loss.
Unknown classification or corruption refuses rather than guessing or deleting.

Clear removes content/grants/derived indexes while retaining configuration;
Factory Reset clears configuration too. Both use the existing retirement and reset
owners. See [StateStore](state-store.md) and [platform](platform-contracts.md).

Implementation: `packages/db`, `packages/assistant-contract`, `packages/state-store`
and `packages/agent-host`.
