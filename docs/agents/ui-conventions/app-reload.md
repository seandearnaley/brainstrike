# App reload — evidence

Supports `docs/agents/ui-conventions.md` § "APP RELOAD".
Read before changing the reload gate, the reload marker, the build id, or proposing an automatic reload.

---

- **2026-09-28 research (BST-1850).** No flagship product silently reloads a live session. Claude desktop is the one that auto-reloads (once, on a chunk failure, then a full-screen "new version" page); its public bugs are exactly the reload loop, where stale cached HTML makes Reload loop (anthropics/claude-code#81961, #64960). That is why the reload is never automatic and why a marker guard exists. Codex desktop leaves a white screen on a failed dynamic import and users restart it (openai/codex#29304, #22688). VS Code web shows a badge and a "Restart to Update" item, always user-initiated. Slack avoids skew by prefetching the next build. Next.js hard-navigates only at a navigation the user started and refuses to reload the current URL. Silent auto-reload was rejected because it aborts web runs and drops unsaved page state.
- **Which capability.** `hasDurableAssistantUsageCapability()` (`packages/assistant-data/src/assistant-durable-usage-capability.ts:21`, the desktop assistant bridge `window.assistant.url|getUrl`) is the existing signal for "the main process owns the run". `use-active-assistant-thread-ids.ts` already reads it as `desktopOwnsRunLifecycle` to skip the renderer sweep because "its main-process stream survives a reload" (assistant-persistence.md, Threads-panel active-run projection), and the run-status reconciliation in `use-assistant-server-run-session.ts` is what reattaches after a reload. Its docstring says "durable usage is recorded here"; the gate does not invent a second probe.
- **Why every resource.** The Threads panel counts one resource (`brainstrike:workspace`, `WORKSPACE_MEMORY_RESOURCE_ID`; `resolveAssistantMemoryResourceId` takes an override only for tests and future scoping). A reload stops every run in the page whichever resource owns it, and the web reap (`reapOrphanedAssistantThreadRuns`) already has no `resource_id` filter, so the gate's query has none either.
- **Unknown is not zero.** `usePGliteLiveQuery` reports `loading: false` with `rows: []` for one render after it is enabled, before its effect flips `loading`. The count query is an aggregate and always returns one row, so an empty result is read as "not delivered", never as zero. A database that is not open, a reap that is idle, pending or failed, a failed query, and a gate that is not observing yet (below) are all non-`ready`.
- **When the gate observes (BST-1850 review, 2026-09-28).** `useRunningAssistantRuns` starts the shared web startup reap and the live query only when `useAppReloadState().required` AND the thread store holds the workspace resource (`Object.hasOwn(threadsByResourceId, WORKSPACE_MEMORY_RESOURCE_ID)`, the Threads panel's and tab strip's `schemaReady`). The reap store is memoised per `DbHandle` and never retries, so starting it before that gate would let one early failure leave both readers in `error` for the whole session (`web-startup-reap.ts` keeps the rule). `required` is set by the `vite:preloadError` listener, and every `requestAppReload` caller is failed-chunk UI shown only after it, so a session that never fails a chunk pays for no `COUNT(*)` live query on `brainstrike_assistant_thread_runs`. A request before then reads `loading` and fails closed to the unknown dialog, which the web E2E's `askForReload` already retries through while the reap and count deliver. The same expression is written inline in `threads-panel.tsx` (twice), `assistant-thread-tabs-workspace.tsx` and `worktree-map-surface.tsx`; keep them in step. If no surface ever loads the workspace thread list, the gate stays unknown (Reload now and Cancel only), never zero.
- **Capability read once.** `AppReloadGate` reads `hasDurableAssistantUsageCapability()` in a `useState` initialiser: the two gates are different component types around the whole shell, so an answer that changed after the first render would remount the application.
- **Decision is taken at the request.** A request with `ready` and 0 runs reloads; anything else opens a dialog whose variant is frozen at that moment. "Reload when finished" waits on a derived `reloadIsDue` boolean (not on the snapshot object), so an equal later snapshot cannot reload twice, and a wait that finds the count unreadable shows the unknown-state dialog again and clears itself when readable. There is deliberately no ref-based once-guard: a reload the browser cancels (a `beforeunload` prompt) would leave it set forever, while a boolean-keyed effect re-arms on the next transition.
- **Marker and factory reset.** The marker is session-scoped, written immediately before a reload and deleted at the next startup. `clearBrowserStorage()` in `packages/app-state/src/factory-reset.ts` ends with a blanket `sessionStorage.clear()`, so it needs no per-key wiring (the composer-draft key relies on the same clear); `chunk-reload-guard.test.ts` runs the real `clearPersistentUiState` to pin that.
- **Build id.** `buildIdPlugin` (`packages/build-utils/src/build-id.ts`) is a Vite plugin `config` hook so both `defineConfig` objects stay static and `command` is known. Web: `VERCEL_DEPLOYMENT_ID`, `VERCEL_GIT_COMMIT_SHA`, `GITHUB_SHA`, then `git rev-parse HEAD`. Desktop: the package version. Turbo's strict env mode hides the CI variables from `turbo run build`, so a turbo build resolves the git HEAD; a cache replay keeps the sha of the first build, which is right because the bundle is identical. Vercel's final `pnpm build` runs vite directly and sees the deployment id.
- **Known limits.** The reap keeps a 60 s clock-skew band, so a run a dead tab left `running` within 60 s of this page's boot is counted (the Threads panel shows the same spinner). `cancelling` runs are not counted, matching the Threads-panel projection. The web startup reap can be started by any tab (pre-existing).
- **E2E and deploy guards (BST-1850, 2026-09-28).** Web `apps/web/e2e/app-reload-recovery.test.ts` (`@web-smoke`) fails the Library Prompts chunk on the built preview and drives the real gate; desktop `apps/desktop/e2e/app-reload-recovery.desktop.test.ts` fails the Terminal chunk (nightly regression, not the PR smoke lane, which is a measured file list). Reloads are counted as main-frame navigation REQUESTS: `framenavigated` also fires for same-document history changes, and an init-script counter in `sessionStorage` is owned by the app, cleared by factory reset and shared with same-origin iframes.
- **Which chunk fails.** The built prompt manager (`connected-prompt-manager-<hash>.js`) is shared with the startup graph, so a name glob alone 404s the app. The lazy import target is a tiny re-export chunk with the same prefix that is requested only when Prompts opens; the spec 404s every match the page had NOT loaded at startup, which is also how a deploy that replaced the hashed files fails an old page. Desktop loads `file://`, which `page.route` cannot intercept, so the chunk is cancelled in the default session's `webRequest`; the build output is never touched. The desktop renderer inlines the prompt manager, so Terminal is its lazy chunk.
- **Web E2E stores are relaxed.** `wasm-loader.ts` opens `web-e2e-*` `idb://` stores with `relaxedDurability`, where PGlite's `syncToFs()` fire-and-forgets (verified in the 0.5.8 dist), so a row seeded through the hooks may not survive a reload right after. The run-gate specs therefore seed the run in the running page and wait for the Threads panel spinner, the same table change the gate counts, before asking. A reload that finds no run counted rightly reloads, so seeding across a reload was tried first and lost the row about half the time.
- **index.html.** Vercel's default for a file with no rule is `cache-control: public, max-age=0, must-revalidate` (vercel.com/docs/caching/cache-control-headers), and `CDN-Cache-Control` and `Vercel-CDN-Cache-Control` outrank `Cache-Control` in its CDN. `apps/web/src/__tests__/vercel-config.test.ts` already pinned "immutable only under /assets/"; that let a year-long `max-age` without `immutable` on the app-wide rule through, so it now allows a cache header only on four reviewed sources that cannot match `/` or `/index.html`.
