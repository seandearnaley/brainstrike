BrainStrike · Research Report · July 25, 2026

Sandboxing the Coding Agent

What Claude Code and Codex actually do, which sandboxing options are genuinely active and canonical in mid‑2026, and which of them fit an Electron desktop app that executes agent commands on end‑user machines across macOS, Windows, and Linux.

TL;DR — Recommendation

Adopt Anthropic's @anthropic-ai/sandbox-runtime (srt) as an embedded library in the Electron main process, wrapping execute_command, the hooks executor, and (later) the agent terminal. It is the same OS‑primitive approach Claude Code ships (Seatbelt on macOS, bubblewrap plus network‑namespace on Linux, proxy‑based egress filtering). It is Apache‑2.0, distributed as a TypeScript library, requires no container runtime on the user's machine, and is under very active development: v0.0.66 shipped July 17, 2026, and it now includes alpha Windows support. Keep the existing permission engine as the policy layer on top (sandbox = blast‑radius reduction, approvals = intent gating; they compose rather than compete). Where the sandbox is unavailable (Windows until the alpha matures, exotic Linux), surface unsandboxed state visibly and keep ask‑by‑default, with no silent fallback.

2How the two reference implementations do it

Claude Code — sandbox-runtime (srt)

Anthropic · open‑sourced · Apache‑2.0 · TypeScript

macOS: Seatbelt via sandbox-exec with dynamically generated profiles. Linux: bubblewrap with the network namespace removed, so all egress must traverse srt's HTTP/SOCKS5 proxies, which enforce domain allow/deny rules. Windows: alpha, using a dedicated user account plus Windows Filtering Platform.

Filesystem read/write allow‑lists and network egress rules per command. Ships as CLI (srt "cmd") and as a library (SandboxManager).

The only vendor approach published as a reusable npm library; directly embeddable in our Electron main process.

OpenAI Codex CLI

Built into codex-rs (Rust) · not a reusable library

macOS: Seatbelt (sandbox-exec profiles per sandbox mode). Linux: bubblewrap plus Landlock and seccomp: read‑only‑by‑default FS with layered writable roots. Windows: after finding AppContainer and integrity levels inadequate, OpenAI built a custom sandbox from restricted tokens, synthetic SIDs, and ACLs: workspace‑only writes and default network blocking without admin rights (announced 2026; WSL2 previously required).

Validates the same architecture (OS primitives, no containers), but it's embedded in their Rust CLI; we'd be reimplementing, not reusing. Their Windows write‑restricted‑token design is the reference blueprint if we ever need Windows enforcement before srt's alpha matures.

The convergent lesson: both vendors rejected containers/VMs for the local case for the same reason we must: you cannot assume Docker, WSL2, or virtualization entitlements on an end user's machine, and a coding agent needs to run the user's real toolchain against the user's real checkout. Both landed on kernel‑enforced policy primitives around ordinary processes, paired with an approval UX for what the policy can't decide.

B. Containers & microVMs wrong layer for local desktop

Docker / Podman All (via VM on mac/Win) Active Requires an install and a daemon/VM we can't assume on end‑user machines; containers see a copied/mounted world, not the user's live toolchain. Viable as an opt‑in “run in container” mode for users who have it.

Watch‑list: excellent future substrate for an opt‑in “clean‑room run” feature on Macs.

C. WebAssembly / WASI different problem

Wasmtime (Bytecode Alliance) is healthy, canonical, and capability‑based by design, but it sandboxes code compiled to Wasm. An agent that needs to run pnpm test, git, and the user's arbitrary toolchain can't live inside WASI. Right tool if we ever ship a plugin system or a bounded compute tool (e.g., safe expression evaluation); wrong tool for the shell surface.

All are real and well‑supported, and all send the user's code and commands to someone else's cloud, against BrainStrike's local‑first, latency‑critical, privacy‑wedge positioning. At most, a future opt‑in “run this remotely” tier. Not the answer for the default path.

E. Language/runtime‑level mostly avoid

  • isolated-vm: officially in maintenance mode (no new features); its author discourages new adoption for untrusted code. Avoid for new work. (vm2, its predecessor, is discontinued with critical CVEs.)
  • Deno permission model: deny‑by‑default capabilities are excellent, but they only govern JS/TS we run under Deno; the moment the agent shells out (--allow-run), the child is unconfined. Not applicable to our Node/Electron runtime.

4Fit analysis & proposed path

0
Keep the permission engine as the policy layer (unchanged role). Sandboxing does not replace approvals; it bounds the blast radius of an approved command. Claude Code's own model is exactly this pairing: sandbox for containment, permissions for intent. Our enforce‑on‑by‑default engine and suspension flow stay the front door.
1
Embed @anthropic-ai/sandbox-runtime in the Electron main process around runShellCommand (the single choke point that execute_command, and eventually hooks, flow through). Default policy: writes confined to workspace roots plus scratch/temp; network deny‑by‑default with a user‑editable domain allowlist (registry mirrors, package hosts) surfaced through the existing approval UI. This aligns with the NO SILENT FALLBACKS rule: sandbox violations should fail loudly with an actionable “allow this path/domain?” prompt.
1b
Reads must be an allow‑list, not a credential deny‑list. Calling this out as a direction decision rather than an implementation detail, because it is the weaker half of the containment story. A deny‑list enumerates badness and will always be incomplete: beyond ~/.ssh and ~/.aws there are ~/.netrc, ~/.config/gh/hosts.yml, ~/.docker/config.json, ~/.npmrc, ~/.gitconfig credential helpers, browser cookie databases, and .env files in other checkouts. Broad reads composed with any reachable egress domain is a working exfiltration channel, and a package registry is reachable by design, so the allowlist that makes the toolchain work is also the one that carries data out. Recommend scoping reads to workspace roots plus resolved toolchain/runtime paths and system libraries, with credential‑path denies kept only as defense‑in‑depth. The sandbox's containment claim is bounded by whichever list is weaker.
2
Platform rollout: macOS and Linux first; Windows stays ask‑only until srt's Windows alpha stabilizes. Sandbox availability becomes a visible capability state (matching the existing capability‑based gating convention, never isElectron()‑style checks): a badge on the run (“sandboxed” / “unsandboxed, approval required”), not a quiet degrade. Re‑evaluate the Windows alpha each srt release; the Codex restricted‑token design is the documented fallback blueprint if we ever must build native Windows enforcement.
3
Complementary, already‑owned pieces: migrate the agent‑facing file tools in assistant-tools.ts off path‑based fsPromises containment and onto secure-fs-native, which already backs the skills and user‑command paths (this is a real gap, not a rename: it closes TOCTOU races that realpath checks cannot); keep worktree isolation for parallel agent runs; wire any new sandbox config store into factory reset per platform contract.
★
Watch list (not now): Apple's container 1.0 for an opt‑in macOS “clean‑room run” (tests in a disposable Linux VM); a Docker/Podman opt‑in mode for users who have it; Wasmtime if a plugin ecosystem ever ships; hosted sandboxes only as an explicit remote tier.

Risks to carry forward

  • srt is a beta research preview: APIs and config formats may shift; pin versions and wrap it behind our own interface so a swap (or a fork) stays cheap.
  • Seatbelt deprecation risk on macOS is real but industry‑shared; Apple breaking it strands Anthropic and OpenAI equally, and srt would be where the fix lands first.
  • Network filtering is allowlist‑quality‑dependent: domain fronting and overly broad FS grants are documented bypass classes; the egress allowlist should ship tight and grow through the approval flow, not default open.
  • The PTY terminal is the hard case: an interactive shell under a sandbox profile changes UX (some tools probe paths the profile denies). Sandbox execute_command first; treat the terminal as its own follow‑up with its own doc.
