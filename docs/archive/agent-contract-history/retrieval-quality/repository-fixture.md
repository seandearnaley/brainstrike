# Repository fixture and evaluation adapter

Supports `docs/agents/retrieval-quality.md`. BST-1922 is the M2 decision gate: hybrid must improve mean recall@10 or MRR by 0.05 without reducing the other. ADR-0017 keeps CLI text retrieval as the default until the required vector capability and quality evidence exist.

The v1 fixture contains 100 distinct authored queries across 21 inspected production modules: 29 exact identifier queries, 14 misspellings, 37 conceptual queries and 20 queries mixing terms and intent. The author inspected implementation source before creating the relevance judgments; these are source-reviewed answer targets, not a claimed human interaction log or output-derived labels. Each target records exact implementation evidence, a rationale and one-based inclusive source lines. Source hashes pin the judgments to main `ed97957e030dd3345c232650199dbc88929dad24`.

The fixture deliberately covers separate aspects of budgets, context packing, file reload ownership, pause leases, worker validation, chunk defaults, worker URL resolution, paths, hashing, URLs, model identity, progress and reciprocal-rank fusion. One known answer span per query makes recall@10 the fraction of queries whose known answer appears. Multiple chunks containing that answer can count in precision; recall counts the answer once. Unjudged useful snippets are not proof of irrelevance. No retrieval output has been used to tune these labels.

`packages/agent/src/evaluation/fixtures/repository-retrieval.json` holds the reviewable judgments. `repository-retrieval.ts` validates source hashes and resolves source-span answers into the existing precision/recall/MRR implementation. The complete candidate corpus is a separate required input and must contain the judged sources. It can include additional source modules and distractors; the 21 positive files are not asserted to constitute repository-wide coverage.

The eval-only adapter takes a search callback returning actual named source pools. Native indexer hits map directly through `chunkId`, `relativePath`, `startLine`, `endLine`, `content` and `score`; canonical host policy additionally requires `startOffset` and `endOffset`. Its validator checks exact source content and offset-derived line ranges, including partial-line AST chunks. Whole-line diagnostic policy is explicit and separately recorded. The callback must implement actual BM25, literal grep, trigram and vector search; missing sources never substitute for one another. Native SQLite BM25 and cosine distances retain their ascending rank order. Fusion reuses `calculateRRFContribution` and `RRF_K_DEFAULT` from the existing database search utility; native score scales never become fusion weights. Each arm supplies 100 candidates; metric output is top 10. BM25 plus grep is the lexical baseline; hybrid adds vectors. Trigram is separately reported, rather than silently replacing grep.

The report records the fixture digest, source revision, candidate corpus hashes, complete embedding profile, derived profile hash, explicit chunking policy, raw candidate pools, final rankings and quality deltas. Any callback rejection or malformed/profile-mismatched pool aborts the report. Metrics are answer-judgment quality, not an inference benchmark or a real-app M2 acceptance claim. Per-arm candidate search durations are captured separately; lexical and hybrid aggregate times sum those sequential callback durations and do not claim consumer latency. The five-point gate permits only one machine epsilon at the subtraction boundary (0.85 minus 0.80); measurable gains below 0.05 remain rejected.

The actual canonical 100-query measurement is recorded in `2026-10-03-canonical-measurement.md`. Its gate failed: lexical recall@10/MRR 0.58/0.44006349 became 0.59/0.41052381 with vectors. All named arms completed on the full source corpus with real renderer embeddings; this measured result does not qualify default vector retention or full real-app M2 acceptance.
