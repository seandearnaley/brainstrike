# Native search execution identity

Readiness observations update semantic availability without replacing execution
identity. Genuine authority, capability, root binding, embedding configuration,
and query-plan changes still cancel active work through the existing controller.

The failed desktop campaign at integration commit
`b7ed0522249ae2bcfe04f405065f6701e8eee6a2` passed eight cases and failed its final
semantic query. Its visible terminal error was
`Native workspace search scope or capability changed.` The trace does not prove
which React dependency changed; that historical attribution remains unknown.

The causal renderer control mounts the actual desktop NativeSearchProvider and
actual app-shell search controller, holds query inference, and supplies a fresh
status DTO with only collection readiness changed. On the original provider this
cancels inference, advances the generation, and fails the query. The RED control
fails specifically at the unexpected cancellation assertion.

The provider now retains a structurally equal execution projection using its
existing JSON equality rule. Only root and collection readiness are removed.
Full observations remain live for availability. Query admission rechecks that
same execution projection against current status before inference.

The paired provider suite passes 23 cases: readiness-only query survival,
readiness availability updates, original cancellation wiring, and genuine
identity-change cancellation. Store, root authority, and collection authority
controls deliberately reuse nested profile and plan references. Additional
controls change profile/hash, query-plan fields/removal, embedding mode,
unavailable authority, the actual bridge capability, and root binding. Late
inference cannot publish after cancellation. The existing controller suite
passes all 23 cases without production controller changes.

These are synthetic status observations in a renderer fixture, not native-engine
or desktop campaign qualification. The desktop campaign and performance run
