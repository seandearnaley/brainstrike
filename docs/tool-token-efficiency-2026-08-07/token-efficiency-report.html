Where our tool tokens go — and how opencode, Cline, and Hermes spend theirs

A source-level teardown of the coding agent's tool-output formats against three popular open-source agents, with ranked fixes. The core finding: our budgets and guardrails are peer-grade or better — the format inside the budget is where the waste is.

Date 2026-08-07 Ours apps/desktop/assistant-server + packages/agent Studied opencode (dev@284214c) · cline (8ca3068) · hermes-agent Method direct source reads; all limits cited from code
01 — Verdict

The budget machinery is fine. The bytes inside it are not.

BrainStrike already has things the three open-source agents mostly lack: deterministic token-denominated budgets enforced on every result, a projection layer that converts raw JSON to text for search tools, offset pagination with mandatory continuation hints (a limited result without guidance fails the run — BST-951), and a durable artifact reader for oversized outputs. Nobody we studied enforces truncation honesty that strictly.

But inside the budget, our grep projection spends roughly 180 characters of envelope per match — a read_args= JSON blob with a 36-char root UUID, a repeated root name, and a per-row source= diagnostic — where opencode spends ~11 and Hermes ~6. Our headers announce four false alarms (candidates_truncated=false | scan_limited=false | …) on every healthy call. Our file reads ship as JSON envelopes, so every newline in file content costs two characters and eleven metadata keys ride along on each page. The result: a 6,000-char grep page holds ~18 matches where a compact format holds ~75, which multiplies tool calls — and every extra call replays the entire conversation. As Cline's own source puts it: "oversized outputs cost quadratically over the remaining run."

The second systemic gap: nothing ever leaves our context. All three peers prune, rewrite, or compact old tool results (opencode clears results beyond a 40k-token window; Cline rewrites superseded file reads to a 40-char placeholder and re-caps every result to 8k chars on every request; Hermes summarizes old tool turns to one line before compaction). We replay every stored projection at full size forever.

The read tool has the same disease

readWorkspaceFile returns {type:'json'} to the model: file content as a JSON string plus eleven metadata keys (content, endLine, nextCursor, omittedChars, path, rootName, size, startLine, tokenCount, totalLines, truncated — including a permanently-null tokenCount). Inside a JSON string every newline is \n (2 chars) and every quote is escaped — a ~2–5% tax on all file content plus the envelope, inside a 6,000-char page. All three peers return plain text with a one-line header/footer. Our unpadded N: line gutter, on the other hand, is exactly what Hermes A/B-measured as optimal (padding cost 16–48% more gutter tokens with zero accuracy gain) — keep it.

04 — What each agent does best

The ideas worth stealing (and the ones we already have)

opencode — spill & delegate

packages/opencode/src/tool · packages/core
  • Save-don't-send: anything over 50 KiB/2,000 lines goes to a managed file; the model gets a bounded preview plus "grep the saved file — or delegate to an explore agent, do NOT read it yourself."
  • History pruning: tool results beyond the newest ~40k estimated tokens are replaced with [Old tool result content cleared].
  • Few-shot .txt descriptions: read teaches its own output format; edit teaches recovery from ambiguous matches; shell has good/bad example blocks.
  • Narrowing over paging: a 100-result cap and one sentence of advice; no cursor machinery at all.

Cline — quadratic-cost thinking

sdk/packages/core/src/extensions
  • Stale-read rewriting: once a file is re-read, the older copy in history becomes [outdated - see the latest file content] — batched at 64 KB reclaimed to protect provider prefix caches.
  • Unconditional 8k re-cap on every tool result on every request build — catches MCP/custom tools uniformly.
  • Middle-truncation everywhere, never silent, always with "which tool/parameter gets you the rest."
  • Command-echo dedup: result echoes only 200 chars of the command — "the full command is already in the tool call input."
  • Model-aware edit routing: GPT/Codex models get apply_patch; others get editor — fewer malformed-edit retries.

Hermes — measure, then optimize

tools/*.py
  • Empirical receipts: the unpadded gutter cites a measured 16–48% saving; zero-match probes cite a 13.9% production zero-match rate; cwd echo cites "60% of calls carry a defensive cd."
  • Loop-breaking: identical reads/searches warn at 3, hard-block at 4: "You already have this information. STOP."
  • Zero-match probes: case-insensitive / hidden-file / literal-string retries turn a dead "0 results" into a steer.
  • Window-scaled budgets: per-result 15% and per-turn 30% of the actual model context, floored and ceilinged.
  • Anti-verification loops: write returns sha256 verified:true — "do NOT re-read the file to check."

BrainStrike — already ahead on

assistant-server · packages/agent
  • Truncation honesty as an invariant: a limited result without a continuation hint throws (BST-951) — no peer enforces this.
  • Deterministic token-denominated budgets with binary-search fitting, per-tool overrides, and a skill-activation carve-out.
  • Durable artifact reader with opaque cursors for oversized results — stronger than /tmp spill files.
  • Hybrid fresh+indexed grep — peers' index-free searches can't go stale; ours can, and the live pass already solves it.
  • Lean tool descriptions — the whole catalog costs ~1.7k tokens.
05 — Proposals

Ranked fixes

Ordered by estimated token impact per unit of effort. P1–P4 are the canonical convergence — every studied agent independently arrived there. P6–P8 are the innovation-token spends.

P1

Path-grouped compact grep projection

impact: very higheffort: M

Rewrite projectGrepSearchModelOutput to group matches by file: one rootName:path header per file (root prefix only when >1 root is open), then   line: text rows. Drop the per-row read_args= envelope and move the "how to read this file" recipe into the tool description once. Same treatment for files mode (path (N matches) per line) and glob. Keep offsets, keep mandatory hints — the BST-951 projector invariants and replay path don't change, only the row renderer. Estimated ~75 matches per 6k page vs ~18 today; proportionally fewer grep calls per task.

From: all three — this is the canonical format (opencode grep.ts:85, hermes _densify_matches, cline search.ts:350).
P2

Silent happy path — flags only when they fire

impact: higheffort: S

Emit candidates_truncated / scan_limited / skipped_missing_line_metadata / liveEngine / source only when true, non-zero, or degraded. Healthy result header becomes grep content 1-50/61. Replace per-row source= with one result-level note only when it matters (e.g. note: live pass skipped — results may be stale). ~120–150 chars saved on every search call, and the model stops reading noise.

From: all three — every peer's healthy output is "Found N matches" and nothing else.
P3

Plain-text projection for readWorkspaceFile

impact: higheffort: M

Replace the {type:'json'} read result with a text projection: one header line (read root:path lines 40-120/540), the numbered content verbatim (keep the unpadded N: gutter — Hermes proved it), and a continue: cursor=… line when truncated. Kills JSON newline/quote escaping (~2–5% of all file content), eleven metadata keys, and the always-null tokenCount. The cursor system stays; it just rides in one footer line.

From: all three — every peer returns plain text pages with a header/footer.
P4

contextLines default 0 in content mode

impact: medium-higheffort: S

Today each content match defaults to 3 content lines (before/match/after). opencode ships no context at all; Hermes defaults to 0; Cline uses 2 but caps at one match per file. Default to 0 and let the model opt in — the matching line plus a cheap targeted read beats paying 3× on every match of every search. With P1's grouped format, adjacent matches also stop duplicating each other's context.

From: opencode (no option exists), hermes (default 0).
P5

Parallel-call nudges + "use the bounded tool" routing

impact: mediumeffort: S

Add one system-prompt rule and per-description phrases: batch independent reads/searches in one turn (fewer turns = the whole history replayed fewer times), and route shell away from cat/grep/find/ls toward the budgeted tools (Hermes: "Do NOT use cat/head/tail (use read_file)…"). Add Hermes' anti-verification line to our write/edit tools: the result already carries bytesWritten/replaced — say "do not re-read to verify."

From: cline (every description + system prompt), hermes (terminal description).
P6

Old-result lifecycle: prune and rewrite history

impact: very high (long threads)effort: L

The biggest systemic win and the right place for an innovation token. Two composable layers: (a) opencode-style pruning — beyond a protected recent window (~40k tokens of tool output), replace old tool-result projections with a one-line marker; (b) Cline-style stale-read rewriting — when a file is re-read or edited, rewrite the superseded read/grep projection to [outdated — see latest read], batched (Cline uses 64 KB reclaimed) to protect prompt-prefix caches. We're unusually well-positioned: model projections are already stored separately from raw results and already have a replay path, so this is a persistence-layer rewrite pass, not a stream change. Our estimator-v2 usage meter gives the trigger signal.

From: opencode (compaction.ts: 40k protect / 20k min-prune), cline (message-builder.ts: OUTDATED_FILE_CONTENT, 64 KB batch).
P7

Loop guards: repeated-call blocking + unchanged-read stubs

impact: medium-higheffort: S–M

Track (tool, args) per thread: identical consecutive grep/read calls get a warning at the 3rd and a hard block at the 4th ("results have NOT changed — you already have this"). For reads, mtime-key the page: an unchanged re-read returns a ~40-token stub instead of the page. Cheap, mechanical, and it caps the classic failure mode where a young agent burns thousands of tokens re-confirming what it already saw. Pairs with P6: after pruning, the dedup cache must reset (Hermes does exactly this).

From: hermes (file_tools.py warn@3/block@4, read-dedup stubs, escalating patch-failure hints).
P8

Zero-match probes on the index

impact: mediumeffort: S–M

When a content search returns zero matches, run up to three bounded probes and report the first that hits: case-insensitive variant, literal-string variant (regex metacharacters that needed escaping), and excluded/hidden-path variant. Hermes measured 13.9% of production searches returning zero — each one currently gives our model nothing to steer by. Our trigram index makes the probes nearly free; the live rg pass covers the excluded-path probe.

From: hermes (_zero_match_probe, file_operations.py:2299).
P9

Shell: 40/60 head-tail split + command-echo dedup

impact: low-mediumeffort: S

Our executeCommand keeps only the tail; Hermes keeps 40% head / 60% tail because compiler and stack-trace errors surface early, and Cline middle-truncates for the same reason. Adopt head+tail retention within the existing budget, and stop echoing long commands back in results (Cline caps the echo at 200 chars — the full command is already in the tool-call input we replay).

From: hermes (terminal_tool.py:3155), cline (RUN_COMMAND_QUERY_PREVIEW_LIMIT).
P10

Instrument before and after

impact: enablingeffort: S

Hermes' habit is the meta-lesson: every optimization above cites a measurement. Before landing P1–P4, add per-tool telemetry to the durable diagnostics store: model-facing chars per call, calls per thread by tool, zero-match rate, and pages-per-search. Re-run the same eval tasks after each change. querySelf can already aggregate this — it just needs the counters written.

From: hermes (measured-decision docstrings throughout).
06 — Overall recommendation

Pick the aggressive-page lane, then make history mortal

On page size the field splits into two coherent strategies: big pages + spill files (opencode 50 KiB, Hermes 100k chars — fewer calls, bigger single results) and small pages + history hygiene (Cline's 8k re-cap, made viable by stale-read rewriting and compaction). Our 6k-char pages put us in Cline's lane — but without the history hygiene that makes that lane work, we currently get the downside of both: many round trips and immortal results.

Recommendation: stay in the small-page lane and complete it. Land the format fixes first (P1–P4 — they make every page 4–5× denser, which is equivalent to a budget raise without touching budgets), add the behavioral nudges (P5), then spend the innovation tokens on P6+P7, which no budget constant can substitute for. Sequence:

  • Wave 1 (format, ~days): P1 + P2 + P4 in one grep-projection PR with before/after fixture snapshots; P3 as a sibling PR. P10 counters land first so the win is quantified.
  • Wave 2 (behavior, ~days): P5 description/system-prompt pass; P8 zero-match probes; P9 shell tweaks.
  • Wave 3 (lifecycle, the innovation spend): P7 loop guards, then P6 pruning + stale-read rewriting driven by the estimator-v2 meter. This is the one that compounds with thread length — the longer the session, the bigger the save.

One caution from the field: Cline batches its history rewrites (64 KB minimum reclaim) specifically because rewriting bytes mid-transcript invalidates provider prefix caches from that point on. Any P6 implementation should inherit that batching from day one.
